# Правила работы ИИ-агентов с проектом

> Обязательный регламент для любой модели (Claude, GPT, и т.п.), которая пишет код в
> этом репозитории. Читается **перед началом работы**. Дополняет, а не отменяет
> [coding-principles.md](coding-principles.md) — «конституцию» кодовой базы: там *как
> устроен код*, здесь *как с ним работать, коммитить и не ломать архитектуру*.
>
> Если правило отсюда противоречит здравому смыслу в конкретной ситуации — не молчи:
> опиши расхождение в блоке «итог» файла [work-history.md](work-history.md) и спроси
> пользователя.

---

## 0. TL;DR (короткая версия для каждого запуска)

1. **Начинай с новой ветки** `agent/<модель>/<краткое-описание>` от свежего `main`.
2. **Записывай ход работы** в конец [work-history.md](work-history.md): промт → тудушник →
   вопросы/ответы → итог. Сам файл **не читай** (он append-only, не источник истины).
3. Пиши код, **переиспользуя** готовые компоненты (§4). Ничего не создаём с нуля, если
   уже есть шаблонный элемент.
4. К БД — **только через `data_base/data_controller.py`** (§5). Прямой ORM в новом коде
   не добавляем.
5. Перед финальным ответом пользователю — **коммить только изменённые тобой файлы**
   (§2). Один коммит = одна законченная порция работы = один твой «готово».
6. Прогони `python manage.py check` и, где уместно, `/verify`.

## 1. Ветки: изоляция каждого агента

Работаем **всегда из отдельной ветки**, никогда напрямую в `main`.

- **Имя ветки:** `agent/<модель>/<slug-задачи>`, например
  `agent/opus/reuse-list-search` или `agent/gpt/fix-calendar-dup`.
  `<модель>` позволяет с первого взгляда отличить, кто из агентов её вёл.
- Ветку создаём **от актуального `main`** (`git fetch && git switch -c ... origin/main`).
  Не наследуемся от чужой незамёрдженной ветки — иначе откат одного агента утянет
  чужие изменения.
- **Один агент = одна ветка на задачу.** Не переиспользуй чужую ветку и не смешивай
  две разные задачи в одной ветке — это ломает атомарность отката (§3).

### Несколько агентов пишут одновременно

Цель: после работы N агентов можно (а) **откатить любого по отдельности**, (б)
получить **единый `main`**, с которого работаем дальше. Как это обеспечивается:

1. **Каждый агент — в своей ветке** (см. выше). Пока агенты работают, `main` не трогается.
2. **Не редактируем одни и те же файлы разными агентами одновременно.** Если задача
   двух агентов пересекается по файлам — это последовательные задачи, а не
   параллельные; распараллеливать по одному файлу нельзя (мердж-конфликты + потеря
   атомарности отката). Разводи агентов по непересекающимся зонам (напр. один — по
   шаблонам, другой — по сервисам).
3. **Каждая ветка мёржится в `main` отдельным squash-мёржем (или merge-commit) и с
   явным описанием.** Один PR = работа одного агента = одна логическая единица отката.
   - Откат конкретного агента = `git revert` его merge-commit’а (или удаление его PR
     до мёржа). Чужие изменения не затрагиваются.
4. **Порядок мёржа — линейный.** Смёржили ветку A → следующий агент **перебазирует**
   свою ветку на обновлённый `main` (`git rebase origin/main`), прогоняет проверки,
   мёржит. Так `main` всегда остаётся зелёным и линейным — «с него можно спокойно
   работать дальше».
5. Если два PR всё же конфликтуют — **конфликт разрешает тот, кто мёржится вторым**, в
   своей ветке, и заново прогоняет `manage.py check` + затронутый сценарий.

> Практическое правило: если сомневаешься, изолированы ли твои изменения — считай, что
> нет, и явно перечисли затронутые файлы в блоке «итог» work-history, чтобы человек
> видел зону пересечения.

## 2. Коммиты: коммить каждый свой полный ответ

Модель фиксирует результат **сразу перед тем, как отчитаться пользователю** «готово,
вот что сделано». То есть текст «вот что было сделано» и коммит появляются **в паре**:
коммит идёт непосредственно перед финальным ответом.

Правила коммита:

- **Коммить только те файлы, которые изменил сам.** Не делай `git add -A` / `git add .`
  вслепую — можно утянуть чужие правки, локальные артефакты (`db.sqlite3`, `logs/*`) или
  сгенерированное. Добавляй файлы **поимённо** (`git add path1 path2`), сверяясь с
  `git status` и `git diff`.
- **Один законченный ответ = один коммит.** Не копи изменения на «потом»: закончил
  порцию работы, о которой отчитываешься, — закоммить её.
- **Сообщение коммита** — по-русски, в стиле истории репозитория
  (`git log --oneline`): `<область>: <что сделано>`, например
  `templates: вынес поиск по таблице в переиспользуемый партиал`.
  При крупных изменениях (§6) — многострочное сообщение с «почему».
- **Не коммить секреты и локальное:** `.env`, `db.sqlite3`, `logs/`, `dev_credentials.md`
  уже в `.gitignore` — не добавляй их принудительно (`git add -f` запрещён без явной
  просьбы пользователя).
- **Хуки не пропускаем** (`--no-verify` нельзя без явной просьбы). Если хук/линтер
  падает — чини причину, а не обходи.
- **Не `push` и не мёрж без явного разрешения пользователя.** Агент готовит ветку и
  коммиты; публикацию/мёрж подтверждает человек (см. §1).

Атрибуция: если среда требует подписи ко-автора — оставляй её, но не подделывай
человеческого автора.

## 3. Откат: как всё устроено, чтобы вернуть назад любого

Атомарность отката держится на трёх вещах:
1. ветка на агента (§1),
2. поимённый коммит только своих файлов (§2),
3. отдельный merge-commit на агента (§1.3).

Тогда:
- **Откатить незамёрженного агента** — просто не мёржить/удалить его ветку.
- **Откатить уже замёрженного** — `git revert -m 1 <merge-commit>`; изменения остальных
  сохраняются, т.к. они в других коммитах/файлах.
- **Вернуться к «чистому `main`»** — `main` и так остаётся рабочим на каждом шаге, потому
  что мёржим линейно и с прогоном проверок (§1.4).

Никогда не делай `git reset --hard` / `git push --force` по общей ветке для «отката» —
это разрушает историю других агентов. Откат — только через `revert` или неслияние.

## 4. Оформление UI: всё переиспользуется, ничего не создаётся заново

**Главное правило вёрстки:** таблицы, календари, всплывающие окна создания объектов,
поиск и добавление, пикеры пользователей/мероприятий — **это готовые шаблонные
элементы**. Их **переиспользуют**, а не пишут заново под каждую страницу.

### Что запрещено

- ❌ Копировать разметку `<table>` + инлайновый `<script>` поиска с одной страницы на
  другую. **Список с поиском** должен собираться из общего партиала списка/поиска, а
  различаться только колонками и источником данных.
- ❌ Писать **второй** календарь / date-picker в шаблоне страницы, когда уже есть
  `initDatepickers`/`.cal-grid`. Нужен диапазон дат — расширяем общий компонент, а не
  клонируем его в новый `<script>`.
- ❌ Своя модалка/чипы/`getlist` выбора «n из m», когда подходит единый виджет
  `data-chip-select` (инлайн/модалка — сам выберет по числу вариантов; для людей —
  `data-select-remote="users"`) или общая модалка `#modal-backdrop`.
- ❌ Инлайновые `<script>` с бизнес-поведением в шаблоне страницы. Общее поведение
  живёт в `base.html` (или отдельном подключаемом JS), навешивается по `data-*`-атрибуту.

### Поведение таблиц (единое для всех списков)

Любая таблица-список (`.responsive-table`) поддерживает **один и тот же набор действий**,
подключаемых атрибутами на `<table>` — не переписывай их для конкретной страницы:

- `data-sortable` — сортировка по клику на заголовок (3 режима: обычный → asc → desc).
- `data-hideable-columns` — **скрытие и возврат колонок в стиле Excel:**
  - в заголовке каждой колонки есть кнопка-«глаз» 👁 — клик прячет колонку (заголовок и
    все ячейки этого столбца во всех строках, включая подгруженные infinite-scroll’ом);
  - когда колонка скрыта, **на границе между двумя соседними видимыми колонками**, между
    которыми есть скрытые, появляется стрелка-указатель; клик по ней **возвращает все
    скрытые между ними** колонки разом (полностью как в классических Excel-таблицах);
  - состояние можно (опционально) запоминать по ключу таблицы — но базовое поведение
    чисто клиентское, без сервера.
- `data-table-filter` — поиск/фильтрация строк (см. пункт «поиск», §A hot-fix).
- `data-infinite-scroll` — постраничная подгрузка.

Нужна новая таблица со списком — включаешь нужные атрибуты, а не копируешь чужой скрипт.

### Как правильно добавить новый элемент

Если действительно нужен **новый переиспользуемый** элемент (которого ещё нет):
1. Реализуй его **один раз** — партиал в `blog/templates/blog/partials/` (разметка) и/или
   `init*`-функция в `base.html`, навешиваемая по `data-*`-атрибуту.
2. Подключай во всех местах через `{% include %}` / `data-*`, без копипасты.
3. Опиши его в таблице выше (обнови этот файл) — чтобы следующий агент нашёл, а не
   создал третий такой же.

## 5. Работа с БД — строго через контроллер

**Целевое правило проекта:** доступ к данным идёт **через
[`data_base/data_controller.py`](../data_base/data_controller.py)**, и напрямую к ORM/БД
не обращается никто, кроме него. Контроллер — единая точка входа: там же аудит-логи
(`logs/db.log`), единообразный матчинг и дозаполнение (напр.
`get_or_create_user_by_telegram_id`).

Правила для нового кода:

- **Новую операцию доступа к данным добавляй как функцию `data_controller`**
  (`create_* / get_* / update_*`), а вызывай её из вьюхи/сервиса/хендлера. Не пиши
  `Model.objects...` в новом коде вьюх и сервисов.
- **Бизнес-логика — не в контроллере.** Контроллер тонкий: только CRUD и простые
  фильтры. Матчинг, пересчёты, ACL — в `blog/services/*` (см.
  [coding-principles.md](coding-principles.md) §1), но сам доступ к строкам они получают
  через контроллер.
- **Тяжёлая аналитика (annotate/aggregate) — через `*_qs()`-аксессоры контроллера.**
  Отчёты (`blog/services/reports.py`, `report_exports.py`) не зашивают агрегацию в
  контроллер (иначе он перестанет быть тонким) и не пишут `Model.objects` (иначе обходят
  правило). Контроллер отдаёт **базовые ленивые queryset'ы** — `events_qs()`,
  `event_shifts_qs()`, `participations_qs()`, `applications_qs()`, `event_staff_qs()`,
  `users_qs()`, `feedbacks_qs()`, `managers_qs()`, `team_leaders_qs()`,
  `dobro_ru_shared_links_qs()` (+ скаляры `get_current_season()`, `get_event_by_id()`), а
  сервис строит `.filter().annotate().aggregate()` поверх них. Именование `*_qs` (в
  отличие от материализующих `get_*`, возвращающих `list`) — сигнал «ленивый queryset для
  композиции». Новую аналитику пиши так же, а не через прямой ORM.
- **Изменяющая операция логируется** (шапка контроллера, [logging.md](logging.md)):
  `INSERT/UPDATE`, с `actor` (кто) и субъектом (над кем).
- Бот и `tg_bot/services.py` — **уже** обязаны ходить только через контроллер
  (async → `sync_to_async` → `data_controller`). Это правило теперь распространяется и
  на веб.

> ⚠️ **Реальность сейчас:** веб-вьюхи и `blog/services/*` исторически используют ORM
> напрямую (это допускала старая редакция coding-principles §1). Приведение к «всё
> через контроллер» — это техдолг, зафиксированный в
> [hot_fix_1.md](hot_fix_1.md). Правило действует **на весь новый код сразу**;
> существующий код мигрируем постепенно и не «размазываем» новый ORM-доступ поверх
> старого.

## 6. Крупные изменения в проекте

Если задача затрагивает архитектуру, схему БД, публичные контракты или много файлов
(«сильные изменения»):

1. **Сначала план, потом код.** Зафиксируй тудушник в [work-history.md](work-history.md),
   при неоднозначности — спроси пользователя (вопросы/ответы туда же).
2. **Схему БД меняем только миграцией** (`makemigrations` → `migrate`), `db_table`
   сохраняем (coding-principles §9). Миграцию коммить вместе с кодом.
3. **Обнови документацию в том же коммите/ветке.** Код и `documentation/*` не должны
   расходиться (coding-principles §10.7). Поменял правило — поменяй доку и, если нужно,
   таблицу компонентов в §4 этого файла.
4. **Крупное = отдельная ветка и отдельный PR** (не смешивать с мелкими правками) —
   чтобы откат (§3) был чистым.
5. **Разбивай на осмысленные коммиты** внутри ветки, каждый с содержательным сообщением;
   финальный ответ пользователю всё равно сопровождается коммитом (§2).
6. Прогони **полную** проверку: `python manage.py check`, миграции применяются на чистой
   БД, затронутые сценарии — вручную/`/verify` (веб — прокликать, бот — прогнать
   команду).

## 7. Файл «история работы»

[work-history.md](work-history.md) — **append-only журнал**. Модели его **не читают**
(это не источник истины и не влияет на решения), но **дописывают в конец** после каждой
задачи. Формат одной записи — в шапке самого файла; коротко, каждая запись содержит:

- **Промт** — что попросил пользователь (дословно/сжато).
- **Тудушник** — план буллет-поинтами (то, что собираешься делать).
- **Вопросы + ответы** — если что-то уточнял у пользователя (пары «вопрос → ответ»).
- **Итог** — что реально сделано, какие файлы затронуты, что осталось/риски.

Зачем это, если модели не читают: это **человекочитаемый след** для ревью и отката —
кто, что и почему менял, какие решения принимались. Не путать с git-историей: git —
про *код*, work-history — про *намерение и контекст*.
