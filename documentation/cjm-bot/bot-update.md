# ТЗ: привести Telegram-бот к целевому функционалу (по деревьям cjm-bot)

> **Кому:** агенту/разработчику, который продолжит работу без контекста предыдущих сессий.
> **Что это:** пошаговое, самодостаточное задание. Целевое поведение бота описано
> интерактивными деревьями в этой же папке (`documentation/cjm-bot/*.html`). Твоя задача —
> реализовать бота так, чтобы он соответствовал деревьям, где блоки помечены 🔶
> «на утверждении» и ✅ «согласовано» (значок в углу карточки узла).
>
> **Главное, что нужно понять сразу:** большая часть «сложной» схемы БД (смены, выбор
> смен в заявке, пошифтовые решения) **уже существует в моделях** — бот её просто не
> использует. Это НЕ переписывание схемы, это подключение бота к тому, что уже есть в вебе.

## 0. Как читать это ТЗ и где что лежит

### Целевое поведение (обязательно открой и просмотри)
Деревья — это источник истины по UX. Открываются двойным кликом, интернета не надо:
- `documentation/cjm-bot/index.html` — обзор + легенда (что значат цвета рёбер и значки ✅/🔶).
- `guest.html` — гость: первое касание, вход через Telegram, регистрация, выбор смен.
- `volunteer.html` — волонтёр: заявки, мои заявки, статистика, подписка, сайт, оценка.
- `team-leader.html` — тим-лидер: свои меро, карточка, заявки (по сменам), явка, тумблер.
- `manager.html` — менеджер: все заявки, публикация меро, рассылка.

Внутри дерева: **узел** = состояние бота (текст ответа + кнопки), **ребро** = действие
пользователя (что нажал). Клик по узлу открывает панель с полным текстом и ветками.
Каждый узел имеет `status: 'approved'` (✅) или по умолчанию `'review'` (🔶). Значок 🔶 =
этот блок изменён по фидбеку заказчика и его надо реализовать/согласовать; ✅ = уже ок.

Текст расшифровки голосового фидбека заказчика (первоисточник правок, с опечатками) —
`documentation/cjm-bot/feed_back.md`. Если дерево и код расходятся — **дерево главнее**,
но при сомнении сверяйся с `feed_back.md`.

### Где код бота
```
tg_bot/
  bot.py                 # сборка Dispatcher, порядок роутеров
  services.py            # СИНХРОННЫЙ сервис-слой: вся бизнес-логика бота здесь
  keyboards.py           # все клавиатуры (reply + inline)
  states.py              # FSM-состояния (aiogram FSMContext)
  ui.py                  # answer_with_expiring_keyboard (inline-кнопки с TTL 5 мин)
  templates_loader.py    # render('имя_шаблона', **kwargs) -> текст из templates_text/*.txt
  templates_text/*.txt   # тексты сообщений (start, help, appnotify, register…)
  notifier.py            # цикл диспетчера уведомлений (очередь bot_outbox + снятие кнопок)
  handlers/
    common.py            # /start, /help, регистрация, /appnotify, deep-links, fallback
    volunteer.py         # /events, подать заявку, /myapps, /stats, /subscribe, оценка
    team_leader.py       # /myevents, обработка заявок, явка, комментарии
    manager.py           # /allapplications, контакты организаторов
    web_access.py        # /webaccess (логин/пароль) — ВОЗМОЖНО заменить на «перейти на сайт»
```

### Ключевые архитектурные правила (НЕ нарушать)
1. **Хендлеры (aiogram, async) только разговаривают с пользователем.** Вся логика — в
   `tg_bot/services.py` (синхронные функции), вызываются через `sync_to_async`.
2. **Сервис-слой НЕ ходит в Django ORM напрямую** — только через
   `data_base/data_controller.py` (`get_*`/`create_*`/`update_*`). Единая точка доступа к БД
   для бота, веба и Mini App. Исключение — уже существующие инфра-модули аутентификации
   (`blog/services/web_auth.py`, `telegram_verify.py`) работают с ORM напрямую, т.к. это
   веб-инфра, а не домен.
3. **Тексты — в `templates_text/*.txt`**, не хардкодь длинные строки в хендлерах. Короткие
   подтверждения можно инлайном, но новые крупные тексты выноси в шаблоны.
4. **Все inline-клавиатуры отправляй через `tg_bot/ui.py::answer_with_expiring_keyboard`** —
   оно ставит кнопки в очередь на снятие через 5 мин (иначе юзер нажмёт кнопку месячной
   давности с неактуальным состоянием). См. `tg-bot.md §0.2`.
5. **ACL проверяй на бэкенде**, не полагайся на скрытие кнопок. Функции прав —
   `blog/services/roles.py` (`is_manager`, `is_team_leader`, `can_process_applications`,
   `has_extended_access_to_profile`).
6. Перед каждым обращением к БД в сервисе — `close_old_connections()` (бот — долгоживущий
   процесс, коннекты протухают). Уже делается во всех функциях `services.py` — повторяй.
7. Бот работает в `ParseMode.HTML` — в текстах используй `<b>`, `<i>`, а команды пиши как
   `/events` (Telegram сам сделает их кликабельными; НЕ оборачивай команду в разметку).

### Как проверять свою работу
- `.venv/Scripts/python.exe manage.py check` — системная проверка Django.
- `.venv/Scripts/python.exe manage.py makemigrations && migrate` — при изменении моделей.
- Синтаксис: `python -c "import ast; ast.parse(open('файл',encoding='utf-8').read())"`.
- Логику сервис-слоя проверяй скриптом через `django.setup()` (см. как это делалось для
  telegram_verify — создать тестовых юзеров/меро, вызвать функции, проверить результат,
  подчистить). Реальный Telegram в этой среде не поднять — прогоняй бизнес-логику напрямую.
- После значимой фичи — запускай бота локально (`manage.py run_bot`, long polling) если есть
  тестовый токен, либо ограничься прогоном сервис-слоя.

## 1. Что УЖЕ есть в схеме БД (использовать, не создавать заново!)

Проверь `blog/models.py` — там уже определены (бот их пока НЕ использует):

- **`EventShift`** (`event_shifts`) — конкретная смена меро: `day`, `recruit_status`
  (`open`/`closed`), `volunteer_needed`, `location`, `confirmed_volunteer`. У каждой смены
  свой набор и своё нужное количество.
- **`Application.selected_shifts`** — M2M на `EventShift`: на какие смены подана заявка
  (чипы на веб-форме). Пусто у Excel-заявок (там только текст в `Application.shifts`).
- **`ApplicationShiftDecision`** — решение (одобрить/резерв) ОТДЕЛЬНО по каждой смене
  заявки. Именно это нужно для «одобрить на смену 12.07, отказать на 13.07» из дерева ТЛ.
- **`Participation`** (`participations`) — участие волонтёра в конкретном дне меро (явка,
  часы). Создаётся при одобрении.
- **`EventStaff`** (`staff_role='team_lead'`) — кто ТЛ на меро.
- **`EventRequirement`** + `blog/services/requirements.py::check_application_requirements` —
  авто-резерв заявки при несоответствии требованиям (уже вызывается в боте).
- **`TelegramAuthToken`** + `blog/services/web_auth.py` — одноразовый вход на сайт по
  deep-link `?start=weblogin`. Уже работает.
- **`User.telegram_verified` + `TelegramVerifyToken` + `blog/services/telegram_verify.py`** —
  фича «Подтвердить телеграм» (СДЕЛАНА, см. §5 ниже — трогать не надо, только знать что есть).

**Вывод:** для выбора смен и пошифтовой обработки заявок в боте новые модели, скорее всего,
НЕ нужны — надо подключить бот к `selected_shifts` / `ApplicationShiftDecision`. Сверься с
тем, как это делает веб (`blog/views.py`: подача заявки, обработка), и повтори в боте.

**B. Вход через Telegram (авторизация по прошлым заявкам)** `[узлы login, login_ok, login_notme]` 🔶 **новое**
- Сейчас: входа-«узнавания» нет. Есть только `/weblogin` (ссылка на сайт) и регистрация.
- Делать: команда/кнопка «🔑 Войти через Telegram». Логика (новая сервис-функция, напр.

  `process_all_applications`.
- Делать: КАЖДАЯ заявка — отдельное сообщение. При действии само сообщение меняет статус
  сверху («Заявка одобрена/в резерве»), кнопки убираются. Если у заявки несколько смен
  (`selected_shifts`) — кнопки ПО СМЕНАМ: `[✅ Одобрить на 12.07]`, `[✅ Одобрить на 13.07]`,
  `[💤 В резерв]`. Тут используешь **`ApplicationShiftDecision`** (уже в моделях). Внизу общий
  `[✅ Одобрить все заявки]`.

**D. Явка / оценка после меро** `[post_event, attend_all, attend_some]` 🔶
- После завершения меро ТЛ просят оценку (как волонтёра) + явку: `[✅ Были все]` / `[Были не все]`.
- «Были все» → авто-`attended` всем, отбивка менеджеру «можно забирать табличку часов»,
  отметка на сайте.
- «Были не все» → ссылка на страницу меро на сайте с **автологином** (переиспользуй
  `web_auth.issue_auth_token` → `/auth/tg/<token>/`, только редирект на страницу меро), явку
  проставляют на сайте.
- Сейчас частично есть `attendance_row` / `services.set_attendance` (пошаговая явка в боте) —
  решить с заказчиком, оставлять ли её или только «все/не все + сайт». Дерево говорит «все/не все».

**E. Тумблер уведомлений о заявках** `[appnotify, app_push]` — ✅ логика есть

## 5. Фича «Подтвердить телеграм» — УЖЕ СДЕЛАНА (справка, не трогать без нужды)

Реализована и в проде. Поток: в ЛК (`profile_edit.html`) кнопка «Подтвердить телеграм» →
`views.verify_telegram_start` (POST) создаёт `TelegramVerifyToken` и редиректит в бота по
`t.me/<bot>?start=verify_<token>` → `common.py::cmd_start` ловит `verify_<token>`, шлёт
«<ФИО> сейчас пытается подтвердить телеграм» + `[✅ Да, это я]`/`[❌ Нет, это не я]`.
- «Да» (`cb_tgverify_yes`) → `telegram_verified=True`, привязка реального `telegram_id` (если
  был `web:*`), кнопка «🌐 Обратно на сайт». При коллизии id — подтверждаем, но id не
  перепривязываем (`conflict`).
- «Нет» (`cb_tgverify_no`) → токен гасится, веб-сессии инициатора удаляются (разлогин).
Логика: `blog/services/telegram_verify.py`; обёртки в `tg_bot/services.py`
(`verify_token_requester`, `confirm_telegram_verification`, `reject_telegram_verification`);
клавиатуры `telegram_verify_prompt`, `back_to_site_button`. Модель: `User.telegram_verified`,
`TelegramVerifyToken` (миграция `0024`).

**Полезное отсюда для §2.1.B (вход через Telegram):** механика deep-link `?start=<payload>` +
одноразовый токен + узнавание пользователя — ровно тот же паттерн, копируй его.
