# Документация базы данных Волонтёрского центра

> **Описание:** Полная схема реляционной базы данных для управления волонтерами, мероприятиями, организациями и обратной связью. Реализована на Django ORM.

---

## Личное оформление (миграция 0048)

`users.appearance`: стабильный идентификатор из реестра `blog/appearance.py`,
по умолчанию `nexus`. `users.color_theme`: `system` (по умолчанию), `light`, `dark`.
Выбор принадлежит аккаунту, одинаков для устройств; смена оформления ручная.
Изменение — сервис `appearance.update_appearance` → контроллер `save_user_appearance`,
в одной записи и с аудитом. ACL административных настроек не меняется.
Подробности: [appearance-system.md](appearance-system.md).

## Миграция старых баз и пул функций (миграция 0049)

Подробно — [legacy-migration.md](legacy-migration.md). Таблицы:

- `legacy_bases` — файл базы целиком (одна база = один год), SHA-256 уникален,
  разобранный план (`parsed`), `people_loaded_at`.
- `legacy_base_columns` — колонка «мероприятие + день»: дата (только явная, иначе
  задаёт человек), `event_group`, `skipped`, `loaded_at`, `value_counts`.
- `legacy_base_people` — строка базы → аккаунт; по ним видно годы баз человека.
- `fap_documents` — все версии ФиП мероприятия (файл, версия, применён).
- `legacy_value_mappings` — уникальное значение ячеек мероприятия → позиция и роль
  (`volunteer`/`team_lead`) или «пропустить».
- `legacy_loaded_cells` — происхождение записей ячейки (позиция, смена, заявка,
  участие, EventStaff): повтор без дублей, перенос при пересопоставлении, откат.
- `position_templates` — типовые позиции пула внутри функции (`event_categories`).
- `profile_conflicts` — расхождение анкеты, которую человек вёл сам, с базой;
  при входе он выбирает актуальное значение.

Миграция 0050: `migration_jobs` (фоновые загрузки: вид, статус, прогресс
`done/total`, `cancel_requested`, `result` — что создано, для отмены; `updated_at` —
сердцебиение), `fap_documents.event_group` может быть пуст (библиотека, `version=0`),
`fap_documents.title/plan` (название по файлу и разобранный план),
`legacy_base_columns.fap_document`. Пул пополнен позициями из реальных ФиП.

`event_categories` теперь — **функции** («Дистанция», «Выдача стартовых пакетов»,
«Проверка медицинских справок»…). Базовый пул (16 функций, 62 позиции) создаёт
миграция 0049 и `seed_data`; прежние тематические категории удаляются, если не
используются. `user_comments.source='legacy_changes'` — журнал изменений данных по
базам (видят только сотрудники о других людях, как остальные `legacy_*`).

## Текущая иерархия: мероприятие → позиция → смена

### FaP / Google Таблицы (миграция 0042)

Мероприятие `EventGroup` связано с одним источником через `event_sheet_links`.
В `template` сохраняется XLSX только с вкладкой «Смены», в `baseline` — последний
согласованный план, отдельно хранятся хеш, предупреждения, Google spreadsheet/sheet ID
и время обмена. Ссылка общая для всех позиций и видна авторизованным участникам.

- `event_directions` — направления внутри мероприятия, порядок и постоянный UUID.
- **С 2026-11-11 (решение пользователя): позиция = строка «Позиция» ФиП** со своим
  количеством и временем по дням, **функция = блок колонки B** (функция позиции —
  `event_category_map` → пул функций с названиями из ФиП). План помечен `row_positions`
  и не сворачивается в направления; описанное ниже «позиция = набор тим-лидера» и
  «количество только из ИТОГО» относится к мероприятиям, импортированным раньше.
- `sheet_positions` — OneToOne к прежнему `Event`. **Позиция = набор одного
  тим-лидера внутри блока «ИТОГО В ЗОНЕ»** (решение 2026-11-11): новая группа
  начинается со строки с другим текстом в колонке тим-лидера, строки без своего
  тим-лидера продолжают текущую. Блок без смены тим-лидеров — одна позиция, как
  раньше. Если у функции несколько групп/блоков, название позиции —
  «Функция — подпись группы» (строка «Тим-лидер …» без префикса роли, иначе первая
  строка волонтёров). Блоки с одинаковой функцией остаются разными позициями.
  Колонка E «Позиция» не создаёт
  бизнес-сущностей и не определяет роли; прежнее поле `is_team_lead_role` сохраняется
  для совместимости. Заявки и участия остаются привязаны к прежним таблицам.
- `sheet_position_days` — исходные рабочее время, check-in/out и количества по датам,
  включая пустоты, нули и неполный план; уникальна пара позиция/дата.
- `sheet_shifts` — OneToOne к прежнему `EventShift`, UUID, ярлык подсмены, плановое
  количество и плановые check-in/out. Фактические отметки остаются в `shift_attendance`.
- `sheet_team_leaders` — имена и необязательная явная привязка пользователя к
  направлению либо позиции. Повторяющиеся подписи внутри направления сводятся в одну,
  но пользователь по имени автоматически не выбирается. Выбор существующего
  тим-лидера создаёт EventStaff на позиции направления; при перепривязке снимаются только
  назначения, созданные интеграцией, ручные назначения сохраняются.
- `zone_responsibles` — отдельная таблица ответственных за зоны (колонка D, «менеджеры
  БС»). Эти записи не создают Manager и не дают права менеджера платформы.
- `google_sheets_connection` — один сервисный аккаунт; JSON-ключ зашифрован Fernet
  ключом, выведенным из SECRET_KEY с отдельным назначением. В интерфейс возвращается
  только email. После смены SECRET_KEY ключ интеграции надо загрузить повторно.

Менеджер может загрузить XLSX или ссылку при создании мероприятия, позднее — через
«Связать таблицу». Открываются только данные «Смены»; ссылки на другие листы исключаются
до разбора XML. Время трактуется в МСК. Количество без времени сохраняется в плане
с предупреждением; фиктивная рабочая смена не создаётся. Импорт создаёт черновики
позиций; публикация остаётся обычным действием платформы.

При чтении FaP набор тим-лидера — одна позиция, один рабочий день — одна смена.
Если блок не делится, количество берётся **только из итоговой ячейки дня в строке
«ИТОГО В ЗОНЕ»**; у разделённого блока количество группы — сумма её строк (итог
зоны общий на все группы). Колонки тим-лидера, ответственных и позиции ищутся по
заголовку строки 1: в реальных ФиП встречается лишняя колонка «Наставник» перед
«Позицией» (`marathon-2026-mentors.xlsx`). В плане у направления сохраняются
`source_rows` (исходные строки E/F) и `code` (`7.2`, `10.4` — совпадает с нумерацией
старой базы); это подсказки миграции, в отпечаток плана они не входят.
Границы смены: самый ранний плановый check-in и самый поздний check-out всех строк
блока за этот день. В `EventShift.start_time/end_time` и `SheetShift.checkin/checkout`
сохраняются одинаковые границы в МСК. Разные интервалы и названия внутренних строк
не создают дополнительные смены; колонка рабочего времени не заменяет check-in/out.
В VIP-блоке `мм.xlsx`: 26.09.2026 — 12 человек, 07:00–13:00;
27.09.2026 — 14 человек, 06:00–17:00. За 24 и 25 сентября смены этого блока нет.

В плане установлен признак `daily_zone_shifts`. Повторная загрузка **того же
исходного файла** исправляет прежнее дробление, сохраняя позиции и первую смену
каждого дня. При локальных правках, заявках или явке автоматическое объединение
блокируется. Старый `repair_direction_import` сохраняется для прежнего разделения
по названиям внутренних строк. Обратный обмен в этой доработке не расширялся.

Дата рабочего дня берётся прежде всего из блока «Кол-во / смена»: заголовок дня
может быть подписью («Pre-race 1»); если дата дня отличается только годом —
предупреждение, а не отказ. Блоков количества может быть больше, чем дней
(«20 июня 1 смена» / «2 смена»): блоки одной даты суммируются в один день, такой
план не переиспользует исходную геометрию при выгрузке. `read_xlsx(default_year=…)`
— год для файлов без года вообще (миграция передаёт год файла/базы).

Распознавание названия листа «Смены», заголовков, итогов и ярлыков подсмен не зависит
от регистра и пробельных символов (включая переносы, табуляцию и неразрывные пробелы).
Исходное написание отображаемых названий и имён сохраняется; совпадение нормализованных
названий не является основанием объединять блоки. Номер в колонке A необязателен;
общие итоги после блоков не импортируются как позиции.

Даты поддерживают Excel-даты/серийные значения, цифровые форматы с точкой, дефисом
или косой чертой, двухзначный год и русские/английские названия месяцев, а также
подписи вроде «Pre-race 24.09». Для короткой даты год берётся из полной даты
соответствующего дня в заголовке работы, check-in/out либо количества. Текущий год
не подставляется. Отсутствие года, повтор дня и расхождение дат между блоками дают
понятную ошибку с колонкой. Поддерживаются объединённые колонки количества разной
ширины, в том числе две колонки в `мм.xlsx` (тестовая копия — `marathon.xlsx`).
В этом примере 24–27 сентября 2026 года и 24 независимых блока.
Пустой день не создаёт смену. Если у дня есть итог, но отсутствует check-in/out,
количество остаётся в плане с предупреждением; время не выдумывается. Если время
есть, но итог пустой, смена также не создаётся. Ошибочный итог блокирует импорт
с указанием ячейки. Сохранённые значения Excel-формул поддерживаются; простой
`SUM(ячейка:ячейка)` и сложение ссылок могут вычисляться без кеша. Внутренние
количества не читаются для набора (кроме ссылок, явно заданных формулой самого итога).

При чтении Google API сначала запрашиваются только названия/ID листов, затем данные
выбранного листа «Смены» с учётом нормализации. Данные остальных вкладок не читаются.

Обмен запускается кнопками «Получить из Google» / «Отправить в Google». Публичный
первый импорт XLSX доступен без ключа. Для API и обратной записи: «План и обмен →
Настроить Google», включить Google Sheets API, загрузить JSON сервисного аккаунта
и выдать его email права редактора нужной таблицы. Код и .env менять не требуется.
После первой привязки следует отправить план в Google для записи стабильных ID.
Подсказка «?» рядом с привязкой содержит шаги и появляется при удержании курсора.

ID позиций/направлений сохраняются в DeveloperMetadata, полный набор ID смен — в
примечаниях ячеек E, как и в XLSX-комментариях `vc_fap:`. При нехватке лимита metadata
используются примечания. Дополнительные видимые вкладки не создаются. Смены с ярлыками
сохраняют ID при перестановке. Новый исходник без ID не объединяется по имени с
существующим планом: для правок следует скачать актуальный XLSX из мероприятия.

Повторный импорт не создаёт дублей; локальные правки не затираются старым планом.
При правках с обеих сторон обмен прекращается с сообщением о конфликте. Удаление
позиций/смен с заявками или участиями блокируется. Сеть и парсинг выполняются до
короткой транзакции записи; Google не держит SQLite write-lock. Google batchUpdate
атомарен, но API не предоставляет здесь compare-and-swap: правка другим редактором
между чтением и отправкой остаётся внешним ограничением, поэтому обмен выполняется
явно по кнопке. В Google изменяется только лист «Смены».

Стили исходников сохранены в `blog/resources/fap/one-day.xlsx`, `three-days.xlsx`
(копии предоставленных примеров). Неизменная геометрия сохраняет стили пустых ячеек,
границы, merges, размеры и freeze panes; расширение дней/направлений использует эти
стили с циклом акцентов. Итоги план/факт и уникальные люди пересчитываются отдельно.
Google использует его собственные форматы: при прежней геометрии возвращаются
исходные userEnteredFormat; при перестроении форматы переводятся из XLSX.

Код: `blog/services/fap_workbook.py`, `event_sheets.py`, `google_sheets.py`; CRUD —
`data_controller/event_sheets.py`. Контракт Google:
[метаданные и их лимиты](https://developers.google.com/workspace/sheets/api/guides/metadata),
[batchUpdate и параллельные правки](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets/batchUpdate).

### Приглашения с выдачей роли (миграция 0043)

- `role_invitations`: уникальный SHA-256 `token_hash CHAR(64)`, выдаваемая роль
  `team_lead` / `manager`, автор, даты создания/истечения и необязательный отзыв.
  Исходный случайный токен в БД не хранится; URL показывается при создании.
- `role_invitation_uses`: приглашение, пользователь и время использования;
  пара приглашение/пользователь уникальна для повторного перехода без дублей.

Менеджер создаёт ссылку в «Настройки → Ссылки приглашения». Роль и срок ссылки
выбираются в общей модалке; значение по умолчанию — 12 часов из
`Const.role_invitation_default_hours`. Ссылка многоразовая до истечения или отзыва.
После входа/регистрации пользователь возвращается по приглашению и сразу получает
постоянную роль через обычный сервис назначения ролей. Истечение ссылки не отзывает
ранее выданные права; анонимный переход по истёкшей ссылке тоже показывает
«срок данной ссылки истек». Отозванная ссылка или ссылка бывшего менеджера недействительна.
Пути `/join/` исключены из технической аналитики, чтобы не записывать токены.

Кнопка «Открыть» в списке приглашений использует общую модалку: профили всех
воспользовавшихся ссылкой и `used_at` в МСК. История доступна менеджеру даже у
истёкшей/отозванной ссылки; повторный переход одного пользователя не дублирует
его и не меняет время первого получения роли. Исходный bearer-токен не выводится.

Справка ПГАС и её верификация скрыты только в HTML-интерфейсе: профили, настройки,
подсказки и инциденты. Модели, формы, сервисы и маршруты ПГАС сохранены.

### Загрузка старой базы (миграция 0047)

> ⚠️ С 2026-11-11 одношаговая «Загрузка базы» заменена поэтапной миграцией (раздел
> выше, [legacy-migration.md](legacy-migration.md)). Ниже — правила чтения анкеты и
> идентичности людей, которые сохранены; мероприятия «по первым цифрам ячейки»,
> условная дата 01.01.2026 и часы 0 больше не применяются к новым загрузкам.

«Настройки → Загрузка базы» принимала XLSX с единственным листом, имя которого
нормализуется до «база»: нижний регистр, NFKC, без пробелов; аналогично распознаются
поля анкеты. Чистый парсер — `services/legacy_workbook.py`; сопоставление, права,
предпросмотр и атомарная запись — `services/legacy_import.py`; CRUD/аудит —
`data_controller/legacy_import.py`. Пределы `Const`: `legacy_import_max_mb` (10),
`legacy_import_max_rows` (10000), `legacy_import_preview_minutes` (60),
`legacy_import_preview_rows` (50 строк на экране); технический
предел 512 колонок. Формулы не выполняются, внешние ссылки Excel не загружаются.
XLSX без необязательных метаданных размера листа (`dimension`) читаются потоково,
без предварительного пересканирования. При неизвестном `max_column` предел 512
проверяется по фактической длине каждой строки, включая заголовок.

План хранится в серверной сессии, привязан к оператору/случайному ID, не попадает
в URL; подтверждение требует POST+CSRF и проверяет срок. До подтверждения нет
изменений профилей/истории. Колонки без точной даты не пропускаются: по явному
решению пользователя им ставится условная **01.01.2026**, позже дата редактируется
на странице смены. Год для дат без года — **2026**. Ошибка
в любой строке, конфликт контактов/мероприятий или повторно изменённая дата смены
откатывают всю операцию. После успеха план удаляется из сессии.

Согласованные правила:
- Имя/фамилия/дата рождения/почта/телефон/соцсети и поля волонтёрства переносятся
  в **новый** профиль; существующие анкеты не обновляются, даже непустыми значениями.
  Если оба имени пустые (или оба старых placeholder=`unnamed`), строка пропускается
  целиком. При одном заполненном имени/фамилии второе поле становится `unnamed`.
  `prepared_plan` применяет это и к ранее сохранённому предпросмотру, пересчитывает
  used по оставшимся назначениям; skipped_rows выводится отдельно.
  Сопоставление по нормализованным Telegram, телефону и почте; если контакты ведут
  к разным аккаунтам, импорт блокируется. Новые аккаунты получают служебный
  `legacy:*` telegram_id, а не чужой VOLUNTEER_ID; реальный TG ID из ника не выводится.
- Telegram хранится без @, VK/Instagram — username без протокола/домена/@/query.
  `social_profiles.py` нормализует импорт и формы профиля; свойства `vk_profile_url`
  и `instagram_profile_url` восстанавливают ссылки для HTML и Excel. Прежние полные
  URL поддерживаются при показе, массового изменения старых анкет нет.
  Если распознать соцсеть нельзя, исходный текст сохраняется (в пределах длины
  поля БД) без предупреждения. Нераспознанный телефон тоже сохраняется текстом.
  Профиль, редактирование и Excel сохраняют эти значения; нераспознанные соцсети
  показываются обычным текстом, без конструирования невалидной ссылки.
- Да/нет распознаются как отдельные слова; неоднозначный ответ — NULL. Размер —
  только XS/S/M/L/XL/XXL/XXXL. Четыре текстовых ответа обрезаются до 255 символов.
  Свободный способ связи, дата анкеты, планы забегов, число смен и VOLUNTEER_ID
  игнорируются. Возраст рассчитывается по ДР; исходное число при наличии сохраняется
  отдельно как reported_age с датой импорта, без выдумывания даты рождения.
  Неподходящие для строгого типа дата рождения/почта/да-нет/размер пропускаются
  без предупреждений о каждой ячейке и без отбрасывания всей строки человека.
- Заголовки дневных колонок группируются в EventGroup; первые цифры ячейки
  (`7.2`, `4.4`, `2`) — название Event-позиции; без цифр — полное название.
  Колонка задаёт отдельную смену на указанную дату. Две колонки одного дня
  («1 смена», «2 смена») остаются отдельными; исходный заголовок сохранён и показан.
- Непустые ячейки дают одобренную заявку/решение и `Participation.status='attended'`
  с 0 часов, full_shift=False. Набор закрыт, публикации/рассылки и роли не выдаются.
  Пока время неизвестно, start_time=end_time=00:00 МСК; `time_unknown` показывает
  «не указано» в позиции/Excel. Обычное редактирование времени пересчитывает часы
  пришедших, если они не были вручную переопределены. Агрегаты пересчитываются.

У неизвестной даты `EventShift.date_unknown` распознаёт условную 01.01.2026 по
сохранённому недатированному source_header. В позиции/Excel она подписана как
условная; отдельной колонки БД не требуется. Повторный импорт не заменяет дату
этой смены, если менеджер исправил её в системе. Явно заданные даты по-прежнему
проверяются на несовпадение источника.

Кнопка подтверждения находится над таблицами; отправка показывает индикатор.
На экране только первые 50 человек, полный план импортируется целиком. Даты
свёрнуты в details с общим календарём. Ошибки подтверждения выведены сверху со
ссылками к полям, валидные исправления дат сохраняются; action содержит якорь
`#legacy-import-status`, поэтому длинный предпросмотр не скрывает причину отказа.

`legacy_import_identities`: уникальный 64-символьный отпечаток контакта либо
ФИО/ДР → User, исходный reported_age (nullable), imported_at. Отпечаток обеспечивает
повторную загрузку без дублей; не является старым ID. `legacy_import_shifts`:
уникальный отпечаток позиции/заголовка → EventShift (one-to-one), source_header.
Перестановка колонок, пробелы/регистр не создают новые копии той же смены.
Свободный текст контактов, пунктуационные заглушки TG и нулевой телефон не служат
идентификаторами. Когда нет распознанных контактов и часть ФИО равна `unnamed`,
отпечаток включает номер исходной строки: разные безымянные строки не склеиваются,
повтор того же файла без перестановки строк не создаёт дубли.

`user_comments.source` (новое поле, индекс) различает `legacy_coordinator` и
`legacy_team_lead`. Комментарии импортируются отдельно с подписью происхождения
и автором загрузки, повтор текста не дублируется. Их видят менеджер/ТЛ в **чужом**
профиле; владелец (даже с ролью) и обычный волонтёр не видят. Обычные внутренние
комментарии сохраняют прежний контекстный ACL; чужие права редактирования не расширены.

### Личный QR и фактическая явка

- `user_qr_codes`: OneToOne `user_id`, уникальный `token VARCHAR(32)`. Это 32 ASCII-байта
  случайного идентификатора; PNG не хранится ни здесь, ни в `users`. Код создаётся
  лениво при первом запросе, остаётся постоянным. QR строго version 2-L, byte mode,
  25×25 модулей; профиль и обычные запросы пользователя эту таблицу не загружают.
- `qr_scanner_grants`: пользователь, мероприятие `EventGroup`, автор/дата назначения
  и `revoked_at`. Отдельный доступ не присваивает роль тим-лидера. Активная пара
  пользователь/мероприятие уникальна; отзыв сохраняет историю.
- `shift_attendance`: уникальная пара пользователь/смена, `entered_at`, `exited_at`,
  автор входа и автор выхода. Повторный вход/выход не меняет уже записанное время.
  Выход без входа и выход раньше входа запрещены. Сам просмотр QR ничего не отмечает.
  Миграция 0046 разрешает пустой `entered_at`: при снятии входа оба времени очищаются,
  строка сохраняется для повторного редактирования прошедшей смены. Пустая строка
  не считается открытым входом и не выводится как последняя отмеченная смена.
- `shift_meals` (миграция 0045): пользователь, смена, время и автор выдачи обеда;
  уникальна пара пользователь/смена.
- `event_badges` (миграция 0045): пользователь, мероприятие `EventGroup`, время и
  автор выдачи значка; уникальна пара пользователь/мероприятие. Несколько позиций
  и смен одного мероприятия не дают дополнительных значков.

В таблице набора позиции (`event_detail`) есть «Обед» на конкретную смену и
«Жетон» на всё мероприятие (та же `event_badges`, что «Значок» в QR). Жетон
синхронизируется во всех строках человека на странице; второй обед другой смены
независим. Таблица сохраняет выдачу сразу, QR — по-прежнему при закрытии окна.
Оба клиента используют `blog/services/handouts.py`; новых таблиц или полей нет.
Состояния выдачи загружаются двумя запросами на позицию, без запроса на каждую строку.

Явка `Participation.status` теперь имеет четыре состояния: `pending` («Не отмечен»),
`attended`, `absent_excused`, `absent_unexcused`. Одобрение заявки создаёт `pending`
с нулём часов. На входе ставится `attended`, часы пока нулевые; на выходе начисляется
фактическое время между входом и выходом с округлением до 0,01 часа. Точные временные
отметки сохраняются отдельно. `Participation.hours`, `User.total_hours` и
`User.season_hours` — DecimalField с двумя знаками. Агрегаты пересчитываются в той же
транзакции. Незакрытый вход и неотмеченная явка блокируют завершение позиции.

Миграция 0041 переводит прежнюю автоматическую явку ещё не начавшихся смен в pending,
пересчитывает агрегаты затронутых пользователей; прошедшая история и записи с ручной
корректировкой часов (`hours_overridden`) остаются нетронутыми.

Сканер доступен менеджеру, ТЛ и пользователю с отдельным назначением. По согласованному
режиму `Const.qr_scanner_scoped_access=0` каждый оператор сканера может отмечать всех.
Значение 1 включает разграничение: менеджер — все смены; ТЛ — свои позиции через
EventStaff; отдельное назначение — позиции указанного EventGroup. Просмотр показывает
все ещё не отмеченные будущие/текущие смены участника, затем прошедшие внутри идущего
мероприятия, по возрастанию даты. Идущее мероприятие определяется интервалом от
первой до последней смены его позиций. Незакрытый вход остаётся доступным для выхода
даже после окончания этого интервала. Личные контакты в карточке сканера не выводятся.

Карточка показывает размер футболки, ссылку на профиль, таблицу смен с галочками
входа/выхода/обеда и отдельный список мероприятий с галочкой значка. Выдача обеда
и значка ручная (подтверждено пользователем): 3 смены дают возможность отметить
3 обеда и один значок, в том числе при сменах разных позиций одного мероприятия.
Последняя QR-отметка показывается отдельно. Ранее сканированные смены сохраняются
в таблице и после окончания мероприятия, включая снятые отметки; ручная явка без
QR не становится новым входом. ACL и запрет изменений завершённой позиции действуют.

Пока окно открыто, установка и снятие галочек — обратимый клиентский черновик. При закрытии
общая модалка ждёт один POST `qr_commit`: сервер атомарно сохраняет выбранные
действия. Если одно действие неверно, весь пакет откатывается, окно остаётся открытым
с ошибкой. Уже сохранённые галочки также доступны для снятия и повторной установки:
пакет передаёт `checked: true/false` (отсутствие поля означает true для совместимости).
Снятие входа снимает также выход и возвращает явку в pending; снятие выхода обнуляет
часы, сохраняя вход. Снятие обеда/значка удаляет запись выдачи с аудитом в `vc.db`.
Повторная установка существующей отметки не меняет её время и не создаёт дубликат.
Время всех новых отметок — **серверное время исходного сканирования**, а не клика
или закрытия; подпись связывает время, оператора и владельца QR. Контекст живёт
`Const.qr_scan_window_minutes` минут (по умолчанию 720), лимит пакета —
`Const.qr_scan_max_changes` (по умолчанию 100). Часы пересчитываются из фактических
входа/выхода в той же транзакции, как и прежде.

Переход из карточки в профиль временно сохраняет токен, подписанный контекст и
выбор в sessionStorage текущей вкладки с ключом оператора. «Назад» восстанавливает
то же окно с прежним временем и черновиком; BFCache использует живую карточку.
Сам переход в профиль отметки не подтверждает. После закрытия черновик удаляется.
При выгрузке страницы вне перехода в профиль используется fetch keepalive;
повторная отправка безопасна. Токен не добавляется в URL и не логируется.

В режиме камеры закрытие карточки автоматически возобновляет сканирование тем же
потоком. Пока карточка открыта, обработка кадров приостановлена. Тот же QR,
оставленный перед камерой, повторно не открывается: нужен другой код или кадр без
кода. Явная остановка, уход со страницы и удаление панели освобождают камеру;
после перехода в профиль и возврата режим восстанавливается вместе с карточкой.
Старый URL `qr_mark` принимает все четыре действия и снятие, новые клиенты
используют пакетный `qr_commit` при закрытии.

«Записать на смену» использует ручное создание заявки и одобрение одной смены
(`create_manual_application` → `process_shift_decision`), сохраняя остальные выбранные
смены и решения. Выбор содержит текущие и будущие смены с открытым набором,
незавершённой позицией и без уже существующего участия; область прав совпадает с
правом отметки. Требования позиции проверяются до одобрения. При старте не позднее
чем через `Const.qr_enroll_checkin_lead_minutes` минут (по умолчанию 60), включая уже
идущую смену, веб-карточка выбирает вход в черновике: он сохраняется только при
закрытии окна, выбор можно снять. Для более поздней смены создаётся только `pending`
без часов. Выход всегда отмечается отдельно; повторная запись не создаёт дублей
и не меняет время входа. Служебный прямой вызов enroll_scanned_user сохраняет
прежнее поведение, веб использует enroll_scan_context с отложенным входом.

### Excel-реестр людей по мероприятию и позиции

`blog/services/roster_exports.py` объединяет **все** заявки (новые, одобренные,
резерв и отменённые) и участия, а не только фактическую явку. Это рабочий файл
до начала смен. Запросы только читают данные, не создают ленивые решения заявок.
Ссылка мероприятия — `/events/groups/<id>/volunteers.xlsx`, позиции —
`/events/<id>/volunteers.xlsx`.

Лист «Участники»: имя, фамилия, полных лет на текущую дату МСК, дата рождения,
почта, телефон, Telegram, ссылка ВК, Instagram, способы связи, размер футболки,
число разных смен в выбранном охвате. Далее одна колонка на **дату начала смены
по Москве**, с названием мероприятия и полной датой. Несколько смен одного дня
перечислены в одной ячейке отдельными строками: позиция, время, решение заявки
и явка при наличии. Для ночной смены дополнительно указана дата окончания.
Пустая ячейка означает отсутствие заявки/участия на этот день.

Человек с `User` выводится один раз по user_id, даже если у него несколько
заявок, позиций и смен. Заявки без привязанного пользователя также выгружаются:
из них доступны имя, фамилия, телефон и Telegram; остальные поля пустые.
Такие заявки не склеиваются по совпадению ФИО: ключом остаётся application_id.
Если смены заявки явно не выбраны, действует существующее правило
`application_shifts`: все смены её позиции. Участие подтверждает запись на смену
даже без заявки. Несколько источников одной смены не удваивают «Число смен».

Лист «Сводка» содержит итог и строки по позициям: уникальных людей, смен,
записей на смены, одобренных/новых/резерва/отменённых записей и явку «Был».
Люди с заявкой на позицию без смен учитываются в количестве людей с нулём смен.
Даты рождения — даты Excel, телефон и пользовательские строки — текст, включая
строки с начальным `=`. Закреплены заголовки и первые две колонки, включён фильтр.

### Московское время

Для одновременной работы сканера, бота и аналитики локальный SQLite использует
`journal_mode=WAL` (`OPTIONS.init_command`), `transaction_mode=IMMEDIATE` и ожидание
блокировки до 20 секунд. WAL позволяет читать подтверждённые данные параллельно
с записью; IMMEDIATE устраняет конфликт повышения read-lock в write-lock внутри
atomic. Одновременные записи по-прежнему сериализуются. Прежний режим DELETE
вызывал периодические задержки переходов до 20–26 секунд и `database is locked`.
После первого подключения с новой настройкой WAL сохраняется в самом файле БД.
Для применения остальных исправлений к запущенному `runall --noreload` нужен перезапуск.

`TIME_ZONE=Europe/Moscow`, `USE_TZ=True`: хранение timestamp в UTC, календарные решения
через `timezone.localdate()`, показ — в МСК (UTC+3), сравнение моментов — aware datetime.
Проверяется граница 22:30 UTC = 01:30 следующего дня в Москве. Форматтеры отчётов,
возраст, текущий сезон, статусы смен, списки бота и таймлайны используют московскую дату.

В интерфейсе списка мероприятий добавлен верхний уровень `EventGroup` (`event_groups`).
Его поля: `title`, `created_at`, M2M `managers` → `users`. Менеджеры выбираются из
пользователей с активной ролью менеджера; назначение не изменяет бизнес-роли.

Прежняя модель `Event` и таблица `events` теперь представляют **позицию**.
Связь `Event.event_group_id` → `event_groups` задаёт родительское мероприятие;
обратная связь — `EventGroup.positions`. Удаление родителя с позициями защищено
через `PROTECT`. Поле допускает NULL для совместимости старых операционных команд;
форма позиции сохраняет родителя, а старые вызовы без поля используют первую группу.
Миграция 0039 присоединяет существующие позиции к общему мероприятию, сохраняя их ID,
смены, заявки, участия и назначения. Демо-база отдельно распределена на три мероприятия.

`EventShift` / `event_shifts` остаются сменами позиции. `Application.event_id`,
`EventStaff.event_id`, решения по сменам и участия сохраняют прежние связи с позицией.
Нижеследующие исторические разделы со словом «мероприятие» и `events` относятся
именно к позиции; старое название `event_days` означает текущие `event_shifts`.

Сводки нового уровня рассчитываются в `blog/services/event_groups.py`:

- набор: сумма одобренных решений по сменам / сумма нужных мест на всех сменах позиций;
- заявки: обработанные / все заявки позиций, без отменённых; многосменная заявка
  считается один раз, в отличие от количества мест в наборе;
- Добро.ру: «проставлено», когда отмечены все позиции с учётом часов; позиции
  `dobro_ru_link_kind='none'` не блокируют сводку. Если учитываемых позиций нет,
  показывается «не требуется». Отдельный дублирующий флаг в `event_groups` не хранится:
  при следующем чтении списка видны отметка, снятие отметки, перенос и удаление позиции.

Дашборд, отчёты, бот и обработка заявок продолжают работать с позициями (`Event`).
Автоматическое наследование назначений/прав от нового мероприятия не вводилось.

Миграция `0044_volunteer_profile_fields` добавляет новые поля анкеты и **удаляет
столбцы `faculty`, `education_program`, `admission_year` со старыми данными**, а также
эти ключи из `verified_snapshot`. Удаление явно подтверждено пользователем.
Старые Word-плейсхолдеры учебных данных ПГАС заменяются пустыми строками; эти поля
больше не требуются для выдачи справки или верификации. Остальные проверки и
маршруты ПГАС сохранены, интерфейс ПГАС остаётся скрытым.

Способы связи: `any` (не принципиально), `telegram`, `vk`, `phone` (звонок), `max`,
`email`, `sms`, `whatsapp`, `viber`. Сохраняется список кодов; форма требует хотя бы
один и допускает несколько, модель проверяет тип списка и допустимые значения.
У существующих пользователей и гостей остаётся `[]` до заполнения формы.
Да/нет хранится как BOOLEAN; NULL означает отсутствие ответа. Футболка хранится
только буквенным размером; справка XS–XXL находится в общем HTML-партиале и не
дублируется в БД. XXXL доступен без выдуманных измерений.

Все пять новых текстовых полей ограничены 255 символами. В анкете на сайте нет
постоянного счётчика: подсказка появляется только на maxlength, сервер отклоняет
превышение. Поля редактируются общей `ProfileForm`. Владелец видит анкету только
при заполнении, на собственной главной она скрыта. Менеджер и ТЛ видят анкету
в чужом профиле; прочие данные сохраняют прежний расширенный ACL. Публичная
страница опыта анкету не раскрывает. Базовая регистрация в боте и допуск к заявкам
не расширялись.

Шкала заполненности считает **всю анкету — 20 полей** (решение пользователя),
по 5% за поле. Множественный выбор контактов — одно поле, ответ «нет» — заполненное
поле; NULL, пустая строка и пробелы не считаются. Состав полей и разделов задаётся
единожды в `blog/services/profile_completion.py`; процент не хранится в БД.
Маленькая шкала находится сбоку в заголовке. В редактировании она обновляется
при вводе, в профиле показывает сохранённые
данные. Ошибочные ответы bound-формы не повышают серверный процент. Форма разделена
на основные данные, контакты и волонтёрство. Пустая дата рождения не подставляется
календарём, дату можно очистить. Правила допуска к заявкам и выдачи ролей прежние.

Ненужные расчёты курса/выпуска и контекст `course_info` удалены. Учебные имена
остаются только как совместимые ключи старых Word-шаблонов (заменяются пустыми
строками), в исторических миграциях и в регрессионных проверках. Действующая модель
и SQL не запрашивают удалённые колонки. При `OperationalError` после миграции нужно
перезапустить старые процессы Django/бота, запущенные с прежней моделью.

### `thank_you_letter_templates` — Шаблоны благодарственных писем

Хранятся только шаблоны. Сами письма **не хранятся** — генерируются на лету при запросе (связь «мероприятие → шаблон» через `events.letter_id`). Два режима (см. `documentation/letter-templates.md`, `blog/services/letter_render.py`):

1. **Конструктор поверх PDF (основной).** Менеджер загружает оформленный **PDF-фон** (`background_pdf`, байты в БД — нет MEDIA-тома, как у `pgas_certificate_template`) и в браузере (`static/blog/js/letter_editor.js`, вкладка настроек «Шаблоны писем») расставляет поверх него поля-заглушки. Их конфигурация — `fields_json`: массив `{key, x, y, w, h, font_id, size, color, align, [text]}`, где `key ∈ {fio, event, event_date, hours, organizer, custom}`, а `x/y/w/h` — **доли [0..1]** от размера страницы (устойчивы к масштабу/DPI). При выдаче письма **PyMuPDF** штампует реальные значения (ФИО, мероприятие, диапазон дат смен, часы, организатор/подпись) в эти координаты поверх фона — кросс-платформенно (без системных бинарей/шрифтов ОС; шрифт берётся из `letter_fonts`).
2. **Legacy-HTML (fallback).** Если `background_pdf` пуст — рендерится старый `letter.html` по `title`/`description` (обратная совместимость).

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | INT PK | Уникальный идентификатор |

| `pattern_link` | TEXT | Ссылка на файл шаблона (legacy) |
| `background_pdf` | BLOB NULL | Байты PDF-фона (конструктор) |
| `background_filename` | VARCHAR(255) | Имя загруженного PDF |
| `page_width_pt` / `page_height_pt` | FLOAT NULL | Размеры страницы фона в PDF-пунктах (эталон для пересчёта долей) |
| `fields_json` | JSON | Конфигурация полей-заглушек |

### `letter_fonts` — Шрифты для конструктора писем

Справочник шрифтов (.ttf/.otf), которыми штампуется текст поверх PDF. Байты хранятся в БД (`BinaryField`) — чтобы шрифт вшивался в PDF на любой ОС **без установки в систему** (кросс-платформенность). Встроенные шрифты (`is_builtin`, DejaVu Sans/Serif/Mono с кириллицей) досоздаются лениво из matplotlib (`blog.services.letter_render.ensure_builtin_fonts`) и не удаляются из UI; свои менеджер загружает в редакторе шаблона.

## Бизнес-правила и логика

1.  **Кэширование статистики:** Поля `total_hours`, `season_hours`, `total_event_count`, `season_event_count` в таблице `users` являются агрегированными (учитываются только участия со `status='attended'`). Пересчитываются при изменении статуса в `participations`. Менеджер может редактировать значения `*_hours` вручную.

2.  **Историчность ролей:** Активной ролью считается запись в `managers` или `team_leaders`, где `revoked_at IS NULL`.

3.  **Обработка заявок:**
    *   Менеджер (или тим-лидер на своём меро) принимает (`approved`) или отклоняет (`rejected`) заявку.
    *   `rejected` = «резерв»: при недоборе ранее отклонённые заявки могут быть приняты. Отдельного статуса «резерв» нет — это те же `rejected`.
    *   **Дубли разрешены и не скрываются.** Один пользователь может подать несколько заявок на одно меро (изменил смены/данные, забыл, что уже подавал). Уникального ограничения на `(user_id, event_id)` нет. Менеджер видит все заявки; актуальной считается последняя, но количество заявок показывается точно.

4.  **Связь заявки и участий:** При `approved` заявке автоматически создаются записи `participations` на **все** дни мероприятия (`event_days`). Тим-лидер затем удаляет лишние дни (≈90% мероприятий — однодневные).

5.  **Матчинг заявки с профилем (импорт из формы/Excel, `user_id` пуст):** искать существующего пользователя последовательно — (1) по `telegram_username`, (2) по `phone`, (3) по ФИО. Если совпадений нет — считаем пользователя новым и создаём профиль по данным заявки. При создании нового профиля выполнять проверку на возможные опечатки в ключевых полях (telegram/телефон/ФИО), чтобы не плодить дубли из-за очепяток.

6.  **Требования:** Таблица `user_requirement_exceptions` работает по принципу «белого списка исключений». Если записи нет — волонтёр считается соответствующим требованию.

7.  **People Helped:** Поле `people_helped` в `events` обязательно для заполнения при закрытии смены/мероприятия.

7a. **Полная смена:** тим-лидер при простановке явки может отметить `participations.full_shift`, зафиксировав, что волонтёр отработал полную смену. Признак не влияет на часы (они считаются отдельно), а используется как отметка добросовестного участия.

7b. **Категории мероприятия:** каждое мероприятие относится к одной или нескольким категориям (`event_category_map`). Категории выбираются менеджером из выпадающего списка при создании мероприятия. Новые категории в справочник `event_categories` добавляет менеджер.

7b-perks. **Плюшки мероприятия:** полностью аналогичны категориям — мероприятию можно назначить одну или несколько плюшек (`event_perk_map`, справочник `event_perks`), это бонусы волонтёру за участие (мерч/питание/сертификат). Выбираются менеджером при создании/редактировании меро; справочник ведёт менеджер во вкладке настроек «Плюшки».

7c. **Тумблеры уведомлений:**
    *   `users.notify_new_events` — волонтёр включает/выключает анонсы новых мероприятий (`🔔 Подписка`). Механика: при публикации нового меро диспетчер рассылает анонс всем, у кого `notify_new_events = true`.
    *   `users.notify_applications` — тим-лидер/менеджер включает/выключает уведомления о поступающих заявках. При `false` карточка новой заявки этому пользователю не приходит (заявки по-прежнему видны в разделе меро/`/allapplications`).

7d. **Повторная заявка (изменение данных):** волонтёр всегда может подать заявку. Если у него уже есть активная заявка на это меро — система предупреждает об этом и уточняет, хочет ли он изменить данные, предлагая посмотреть текущую заявку или изменить её. При изменении создаётся **новая** запись `applications`, которая считается актуальной (дубли не скрываются, см. правило 3).

7e. **Учёт часов на Добро.ру (ручная простановка менеджером):**
    *   Тип учёта задаётся на меро в `events.dobro_ru_link_kind`:
        *   `none` — ссылки нет; меро **исключается** из отчёта простановки (часы на Добро.ру по нему не ведутся).
        *   `shared` — часть меро (обычно мелких) учитывается через одну **общую** ссылку `dobro_ru_shared_links`, чтобы не плодить ссылки; несколько меро ссылаются на одну запись.
        *   `unique` — у меро **своя** ссылка в `events.dobro_ru_link` (напр. крупный ДОД на 100 волонтёров).
    *   Простановка — **ручная** операция вне системы (на сайте Добро.ру); в нашей системе менеджер лишь **отмечает факт** простановки, построчно по волонтёрам (`participations.dobro_ru_logged`) или пакетно по ссылке.
    *   Отмечать можно только участия со `status='attended'` и `hours > 0`.
    *   Агрегатный флаг `events.dobro_ru_hours_logged` = true, когда по всем attended-участникам меро проставлено (`dobro_ru_logged`); используется для быстрого статуса меро.
    *   Отчёт простановки строится в двух разрезах: **по человеку** (кому и сколько ставить) и **по ссылке** (какие меро/люди идут в конкретную ссылку) — см. `reports.md` §8.

8.  **Аутентификация (два канала входа в один аккаунт):**
    *   Аккаунт **всегда** создаётся через Telegram; `telegram_id` — первичный источник идентичности. Регистрация через веб без Telegram невозможна.
    *   **TG Bot / Mini App:** вход по `telegram_id` через проверку `initData`, без пароля.
    *   **Web Platform:** вход по `login` + `password_hash`. Логин/пароль задаются при первом касании с ботом; хранятся в `users`.
    *   **Сброс/смена пароля** — только через ТГ-бота/Mini App (`/start` → «сбросить веб-пароль»); self-service сброса на сайте нет.

9.  **Churn (коэффициент недобросовестности):**
    *   `users.churn_score` (FLOAT) — текущее значение на данный момент.
    *   **Начисление:** `+churn_no_show_penalty` (по умолчанию `+1`) за каждое меро с `absent_unexcused` (неявка без предупреждения). Проставляется тим-лидером вручную.
    *   **Списание за активность:** `− churn_activity_base / e^(N + 1)`, где `N` — количество мероприятий, на которых волонтёр был за последний месяц.
    *   **Блэклист:** при `churn_score ≥ churn_blacklist_threshold` волонтёр переводится в блэклист до следующего сезона / учебного года.
    *   **Закрытие сезона:** для всех с ненулевым чарном создаётся запись в `churn_history` (снимок значения), затем в профиле: если у волонтёра уже есть ≥ `churn_carryover_min_seasons` записей в `churn_history` — снимается только половина чарна; иначе — обнуляется.

10. **Статус набора (`recruit_status`):** `closed`, когда количество `approved` заявок ≥ `recruit_close_ratio × SUM(event_days.volunteer_needed)` (по умолчанию 1.2×). Фактическая явка (`attended`) — отдельная метрика, на закрытие набора не влияет.

11. **Сезоны:**
    *   Сезоны **не пересекаются**; даты задаёт менеджер в отдельной вкладке.
    *   Если предыдущий сезон закончился, а следующий не задан — автоматически создаётся новый сезон без даты окончания («до бесконечности»), а менеджерам и тим-лидерам показывается плашка-уведомление о необходимости задать дату конца сезона.
    *   При наступлении нового сезона обнуляются `season_*` поля и выполняется процедура churn-carryover (правило 9).

12. **«Звёздочка ⭐» / закрытие ПГАС:** статус выдаётся автоматически, когда волонтёр набирает `pgas_hours_threshold` часов **за сезон** (считается по `season_hours`). Отдельной сущности достижений нет — это производный признак. Порог `pgas_hours_threshold` — предположение (100), уточнить фактическое значение у заказчика.

13. **Оценка мероприятия и организации:**
    *   Единственная оценка меро — средний рейтинг из `event_feedbacks.rating` (отдельного поля `event_mark` нет).
    *   Оценку организации (`organizations.internal_rating`) и комментарии (`organizations.comment`) ставят/пишут менеджеры (в любой момент) и тим-лидеры (только после проведённого ими мероприятия этой организации). Видно только менеджерам и тим-лидерам.

14. **Константы:** пороги и коэффициенты (churn, ПГАС, множитель набора и т.п.) хранятся в таблице `const`, а не в коде; задаются при инициализации БД и редактируются менеджером.
