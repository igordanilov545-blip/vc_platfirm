## Пользователи и Роли

### `users` — Пользователи (Volunteers)

Центральная сущность системы. Наследуется от `AbstractBaseUser`. Основной вход — через Telegram ID; дополнительно поддерживается вход на Web Platform по `login`/`password_hash` (см. бизнес-правило 8).

| Поле | Тип | Описание | Источник данных |
|------|-----|----------|-----------------|
| `id` | INT PK | Уникальный идентификатор | Автоинкремент БД |
| `system_username` | VARCHAR(50) | Системный логин | Генерируется системой |
| `telegram_id` | VARCHAR(50) | Числовой ID Telegram (уникальный) | Telegram Bot API при первом входе |
| `telegram_username` | VARCHAR(100) | Никнейм в Telegram (@name) | Telegram Bot API при взаимодействии |
| `VK_username` | VARCHAR(100) | VK для связи | Ввод пользователем в профиле |
| `first_name` | VARCHAR(100) | Имя | Telegram API / Форма профиля |
| `last_name` | VARCHAR(100) | Фамилия | Telegram API / Форма профиля |
| `email` | VARCHAR | Электронная почта | Ввод пользователя |
| `phone` | VARCHAR(20) | Номер телефона | Ввод пользователя |
| `birthday` | DATE | Дата рождения | Ввод пользователя |
| `about` | TEXT | Информация о себе | Ввод пользователя |
| `gender` | ENUM(`male`, `female`) | Пол (`male` — мужчина, `female` — женщина) | Ввод пользователя |
| `status` | VARCHAR(20) | Статус: `active`, `inactive`, `blacklisted` | Установка менеджером |
| `comment` | TEXT | Внутренний комментарий менеджера | Ввод менеджером |
| `created_at` | TIMESTAMP | Дата регистрации | Автоматически |
| `last_event_at` | TIMESTAMP | Дата последнего участия | Обновляется системой после меро |
| `total_event_count` | INT | Мероприятий за все время | Агрегат `COUNT(participations)` |
| `season_event_count` | INT | Мероприятий за текущий сезон | Агрегат с фильтром по сезону |
| `total_hours` | INT | Часов за все время | Агрегат `SUM(participations.hours)` где `status='attended'` (менеджер может редактировать вручную) |
| `season_hours` | INT | Часов за текущий сезон | Агрегат с фильтром по сезону (менеджер может редактировать вручную) |
| `churn_score` | FLOAT | Коэффициент недобросовестности волонтёра на текущий момент | Пересчитывается системой, см. бизнес-правила. По достижении порога (`const.churn_blacklist_threshold`) — в блэклист до следующего сезона |
| `login` | VARCHAR(50) | Логин для входа на Web Platform (nullable до установки, unique) | Задаётся при первом касании с ботом |
| `password_hash` | VARCHAR(255) | Хеш пароля для Web Platform (nullable) | Устанавливается/сбрасывается через бот/Mini App |
| `web_credentials_set_at` | TIMESTAMP | Когда установлены веб-креды (nullable) | Автоматически при установке |

### `thank_you_letter_templates` — Шаблоны благодарственных писем

Хранятся только шаблоны. Сами благодарственные письма **не хранятся** — при запросе (скачивание/открытие) генерируются на лету путём подстановки ФИО волонтёра в шаблон. Связь «мероприятие → шаблон» задаётся через `events.letter_id`.

| Поле | Тип | Описание |

| `id` | INT PK | Уникальный идентификатор |
| `title` | VARCHAR(255) | Название шаблона |
| `description` | TEXT | Описание шаблона |
| `pattern_link` | TEXT | Ссылка на файл шаблона |

### `const` — Константы системы

Key-value справочник настраиваемых бизнес-параметров. Значения задаются при инициализации БД и редактируются менеджером в отдельной вкладке (вместе с управлением сезонами). Тип значения — `FLOAT`, чтобы покрыть и целые пороги, и дробные коэффициенты.

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | INT PK | Уникальный идентификатор |
| `name` | VARCHAR(100) | Название константы (уникальное, машинный ключ) |
| `value` | FLOAT | Значение |
| `description` | TEXT | Человекочитаемое описание (для вкладки менеджера) |
| `created_at` | TIMESTAMP | Дата создания |
| `updated_at` | TIMESTAMP | Дата последнего изменения |

#### Обязательный набор констант (seed при инициализации БД)

| `name` | Значение по умолчанию | Смысл |
|--------|----------------------|-------|
| `churn_no_show_penalty` | `1` | Прибавка к чарну за неявку без предупреждения (`absent_unexcused`) |
| `churn_activity_base` | `3` | Числитель в бонусе за активность: `churn_activity_base / e^(меро за последний месяц + 1)` вычитается из чарна |
| `churn_blacklist_threshold` | `5` | Порог `churn_score`, при достижении которого волонтёр уходит в блэклист до следующего сезона |
| `churn_carryover_min_seasons` | `2` | Если у волонтёра уже есть ≥ этого числа заполненных записей в `churn_history`, при закрытии сезона чарн не обнуляется полностью, а снимается только половина |
| `pgas_hours_threshold` | `100` | Количество часов **за сезон** (`season_hours`) для закрытия ПГАС → автоматическая выдача статуса «Звёздочка ⭐» |
| `recruit_close_ratio` | `1.2` | Множитель: набор `closed`, когда одобренных заявок ≥ `recruit_close_ratio × volunteer_needed` |
| `late_cancel_hours` | `24` | За сколько часов до меро отказ считается «поздним сливом» (для будущей калибровки; фиксируется как параметр) |

> Значение `pgas_hours_threshold` (100) — предположение; уточнить у заказчика фактический порог ПГАС.
> Значение `churn_blacklist_threshold` (5) — предположение; калибруется по данным первого сезона.

Снимок значения `users.churn_score` на момент завершения сезона. Формируется при переходе на новый сезон: для всех, у кого есть ненулевой чарн, добавляется запись, после чего значение в профиле обнуляется/уменьшается (см. бизнес-правила).

| Поле | Тип | Описание | Источник данных |

| `created_at` | TIMESTAMP | Дата фиксации (закрытие сезона) | Автоматически |

### `user_comments` — Комментарии к волонтёрам

Внутренние комментарии, которые менеджеры и тим-лидеры пишут о волонтёре. Вынесены в отдельную таблицу (а не поле `users.comment`), чтобы поддержать контекстную видимость для тим-лидера (см. правило 5–6 в `access-control.md`): нужны автор, дата и контекст. Волонтёр свои комментарии **никогда** не видит.

## Бизнес-правила и логика

1.  **Кэширование статистики:** Поля `total_hours`, `season_hours`, `total_event_count`, `season_event_count` в таблице `users` являются агрегированными (учитываются только участия со `status='attended'`). Пересчитываются при изменении статуса в `participations`. Менеджер может редактировать значения `*_hours` вручную.

2.  **Историчность ролей:** Активной ролью считается запись в `managers` или `team_leaders`, где `revoked_at IS NULL`.

3.  **Обработка заявок:**
    *   Менеджер (или тим-лидер на своём меро) принимает (`approved`) или отклоняет (`rejected`) заявку.
    *   `rejected` = «резерв»: при недоборе ранее отклонённые заявки могут быть приняты. Отдельного статуса «резерв» нет — это те же `rejected`.
    *   **Дубли разрешены и не скрываются.** Один пользователь может подать несколько заявок на одно меро (изменил смены/данные, забыл, что уже подавал). Уникального ограничения на `(user_id, event_id)` нет. Менеджер видит все заявки; актуальной считается последняя, но количество заявок показывается точно.

4.  **Связь заявки и участий:** При `approved` заявке автоматически создаются записи `participations` на **все** дни мероприятия (`event_days`). Тим-лидер затем удаляет лишние дни (≈90% мероприятий — однодневные).

5.  **Матчинг заявки с профилем (импорт из формы/Excel, `user_id` пуст):** искать существующего пользователя последовательно — (1) по `telegram_username`, (2) по `phone`, (3) по ФИО. Если совпадений нет — считаем пользователя новым и создаём профиль по данным заявки. При создании нового профиля выполнять проверку на возможные опечатки в ключевых полях (telegram/телефон/ФИО), чтобы не плодить дубли из-за очепяток.

6.  **Требования:** Таблица `user_requirement_exceptions` работает по принципу «белого списка исключений». Если записи нет — волонтёр считается соответствующим требованию.

7.  **People Helped:** Поле `people_helped` в `events` обязательно для заполнения при закрытии смены/мероприятия.

8.  **Аутентификация (два канала входа в один аккаунт):**
    *   Аккаунт **всегда** создаётся через Telegram; `telegram_id` — первичный источник идентичности. Регистрация через веб без Telegram невозможна.
    *   **TG Bot / Mini App:** вход по `telegram_id` через проверку `initData`, без пароля.
    *   **Web Platform:** вход по `login` + `password_hash`. Логин/пароль задаются при первом касании с ботом; хранятся в `users`.
    *   **Сброс/смена пароля** — только через ТГ-бота/Mini App (`/start` → «сбросить веб-пароль»); self-service сброса на сайте нет.

9.  **Churn (коэффициент недобросовестности):**
    *   `users.churn_score` (FLOAT) — текущее значение на данный момент.
    *   **Начисление:** `+churn_no_show_penalty` (по умолчанию `+1`) за каждое меро с `absent_unexcused` (неявка без предупреждения). Проставляется тим-лидером вручную.
    *   **Списание за активность:** `− churn_activity_base / e^(N + 1)`, где `N` — количество мероприятий, на которых волонтёр был за последний месяц.
    *   **Блэклист:** при `churn_score ≥ churn_blacklist_threshold` волонтёр переводится в блэклист до следующего сезона / учебного года.
    *   **Закрытие сезона:** для всех с ненулевым чарном создаётся запись в `churn_history` (снимок значения), затем в профиле: если у волонтёра уже есть ≥ `churn_carryover_min_seasons` записей в `churn_history` — снимается только половина чарна; иначе — обнуляется.

10. **Статус набора (`recruit_status`):** `closed`, когда количество `approved` заявок ≥ `recruit_close_ratio × SUM(event_days.volunteer_needed)` (по умолчанию 1.2×). Фактическая явка (`attended`) — отдельная метрика, на закрытие набора не влияет.

11. **Сезоны:**
    *   Сезоны **не пересекаются**; даты задаёт менеджер в отдельной вкладке.
    *   Если предыдущий сезон закончился, а следующий не задан — автоматически создаётся новый сезон без даты окончания («до бесконечности»), а менеджерам и тим-лидерам показывается плашка-уведомление о необходимости задать дату конца сезона.
    *   При наступлении нового сезона обнуляются `season_*` поля и выполняется процедура churn-carryover (правило 9).

12. **«Звёздочка ⭐» / закрытие ПГАС:** статус выдаётся автоматически, когда волонтёр набирает `pgas_hours_threshold` часов **за сезон** (считается по `season_hours`). Отдельной сущности достижений нет — это производный признак. Порог `pgas_hours_threshold` — предположение (100), уточнить фактическое значение у заказчика.

13. **Оценка мероприятия и организации:**
    *   Единственная оценка меро — средний рейтинг из `event_feedbacks.rating` (отдельного поля `event_mark` нет).
    *   Оценку организации (`organizations.internal_rating`) и комментарии (`organizations.comment`) ставят/пишут менеджеры (в любой момент) и тим-лидеры (только после проведённого ими мероприятия этой организации). Видно только менеджерам и тим-лидерам.

14. **Константы:** пороги и коэффициенты (churn, ПГАС, множитель набора и т.п.) хранятся в таблице `const`, а не в коде; задаются при инициализации БД и редактируются менеджером.
