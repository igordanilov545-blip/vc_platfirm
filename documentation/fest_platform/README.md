# Fest Platform — демо-стенд для фестивалей (разгон идей)

> Статус: **брейншторм / разгон демо**, ещё не реализация.
>
> **Что это на самом деле.** Не приложение и не рабочая система, а **набор
> предзаготовленных красивых HTML-страниц** («кликабельный прототип») — чтобы показать
> заказчику, *как это может выглядеть*. Реальный функционал не нужен: модели, БД,
> оплаты, валидация билетов — **ничего этого нет**. Кнопки — заглушки (попап «TBA» /
> переход между статичными страницами). Ценность демо — в красоте и полноте картины
> «что может быть», техническая реализуемость и так очевидна.
>
> Как встраиваем в текущий проект, не сломав прод — [architecture-fit.md](architecture-fit.md).
> Реестр правок в общих файлах — [core-touchpoints.md](core-touchpoints.md).
> Что потом сможет Telegram-бот (описываем в конце, бота сейчас **не трогаем**) —
> [telegram-bot.md](telegram-bot.md).

---

## 0. Рамки демо (читать первым)

- **Только статичные страницы.** Несколько HTML-страниц с видом пользователя (его
  основные пути) + страница организатора. Всё под URL-префиксом **`/test_stend/`** и
  в отдельной папке.
- **Связь с проектом ВЦ — временная и только ради удобства.** Переиспользуем готовые
  наработки (стили `nexus.css`, вёрстку, компоненты, роутинг Django) исключительно для
  стенда. **В случае контракта — это будет отдельный проект.** Поэтому ЛК гостя,
  аккаунты и т.п. в демо — **самостоятельная система**, не завязанная на аккаунт ВЦ.
- **Все сложные механики — заглушки.** Не тратим силы на то, что не видно на картинке.
- **Telegram-бота сейчас не трогаем.** В конце опишем, что бот *сможет* делать —
  отдельным файлом [telegram-bot.md](telegram-bot.md), без реализации.

## 2. Экраны демо (что именно рисуем)

Каждый пункт — **одна или несколько статичных HTML-страниц**. Кнопки ведут либо на
соседнюю демо-страницу, либо открывают попап-заглушку.

### 2.1. Страница феста (витрина гостя) — **главный экран, максимум красоты**
Одна публичная страница-лендинг:
- Полноэкранный hero: обложка, название, дата, город, **countdown** до старта (можно
  живой на JS — это дёшево и эффектно), крупная кнопка «Купить билет».
- Блоки: о фесте · программа по сценам/времени (таймлайн) · приглашённые гости/артисты
  (карточки) · локация с картой (статичная картинка/встроенная карта) · галерея
  прошлых фестов · FAQ (аккордеон) · партнёры.
- **Тарифная сетка билетов** — таблица «что входит» (✓/—), выделенный «популярный»
  тариф, счётчик «осталось N» (нарисованный).
- **Одна версия страницы** (без служебной/редакторской версии — правки делаются в
  кабинете организатора, п. 2.4).
- Кнопка «Купить билет» → **попап «TBA»** (продажа — заглушка).

### 2.2. Маркет феста — витрина продавцов + предзаказ-заглушка
- Отдельная страница: сетка **продавцов и товаров** (карточки с картинкой, названием,
  ценой, продавцом; фильтр по категории — можно нарисовать неактивным).
- Карточка товара → кнопка **«Предзаказать»** → попап-заглушка («оплата с кошелька —
  TBA» / «добавлено в предзаказы»).
- Идея, которую продаём: гости заранее бронируют товары на маркете, оплата — с
  внутреннего кошелька платформы (в демо только нарисовано).

### 2.3. Личный кабинет гостя — основные пути пользователя
Несколько связанных статичных страниц (**отдельная от ВЦ система аккаунтов**, в демо
— просто «как будто вошёл»):
- **Мои билеты** — карточки билетов с нарисованным QR-кодом и тарифом.
- **Кошелёк** — нарисованный баланс + лента транзакций (пополнение, оплата предзаказа,
  бонусы). Кнопки — заглушки.
- **История посещений** — прошлые фесты, статус «постоянный гость», бейджи/достижения
  (можно переиспользовать визуал достижений ВЦ).
- **Мои приглашения** (см. 2.5) — список инвайтов под каждый фест.

### 2.4. Кабинет организатора феста — «как этим управляют»
Понравившаяся идея — показываем «изнанку»: одна-две страницы с интерфейсом управления,
все кнопки — заглушки.
- Дашборд феста: плитки «продано билетов / выручка / посетителей / предзаказов на
  маркете» (нарисованные цифры) + пара графиков (статичные картинки или лёгкий JS).
- Кнопки-заглушки: **«Добавить фест»**, «Добавить тариф», «Добавить товар/продавца»,
  «Аналитика», «Рассылка», «Выгрузка» — по клику попап «TBA» или переход на
  демо-форму-пустышку.
- Список покупателей / список товаров маркета — нарисованная таблица (переиспользуем
  табличный компонент ВЦ).

### 2.5. Приглашения гостей — заглушка (редкий кейс, минимум сил)
У некоторых типов участников/организаторов есть N приглашений. Реализуем как идею:
- В ЛК гостя — **список приглашений под каждый фест** (нарисованный): «осталось
  приглашений: N», список приглашённых, у каждого статус.
- Механики, которые *обозначаем, но не делаем*: QR/ссылка-инвайт (перейти →
  зарегаться), пригласивший видит, кто зарегался и сколько осталось, может отменить
  инвайт (утекла ссылка / передумал), может добавить вручную по ФИО.
- В демо всё это — статичный список + кнопки-заглушки. Внимания минимум.

## 3. Что переиспользуем из проекта ВЦ (только для стенда)

Берём готовое, чтобы быстро получить красивую картинку:
- **`nexus.css` и темы** (тёмная/светлая) — базовый визуальный язык.
- **Готовые UI-паттерны**: таблицы, карточки, модалки/попапы, аккордеоны, вёрстка
  сетки — как основу, поверх — свой фестивальный стиль.
- **Роутинг Django** — просто чтобы отдавать статичные шаблоны под `/test_stend/`
  (без вьюх с логикой, шаблоны почти статичные).
- **Визуал достижений** — для «бейджей гостя» в ЛК.

Ничего из ядра при этом **не мутируем** (см. architecture-fit.md).

## 4. Приоритет для демо

1. **Страница феста** (2.1) — вау-эффект, вкладываем сюда больше всего.
2. **ЛК гостя** (2.3) — основные пути пользователя.
3. **Кабинет организатора** (2.4) — «изнанка», показывает управляемость.
4. **Маркет** (2.2) — витрина + предзаказ-заглушка.
5. **Приглашения** (2.5) — заглушка, по остаточному принципу.

Продажа билетов, оплаты, сканер входа, реальный кошелёк — **вне демо**
(кнопки-заглушки «TBA»).
