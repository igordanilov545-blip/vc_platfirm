# Как встроить демо-стенд Fest, не сломав прод

> Технический договор о том, *как* демо-страницы Fest живут рядом с текущей платформой.
> Идеи и экраны — в [README.md](README.md). Реестр правок в общих файлах —
> [core-touchpoints.md](core-touchpoints.md).
>
> **Важно.** Это **демо из статичных HTML-страниц**, а не приложение. Поэтому большей
> части «архитектуры» тут нет: **нет моделей, нет миграций, нет БД-логики, нет
> сервисов с бизнес-правилами**. Есть лишь несколько шаблонов, которые Django отдаёт
> под префиксом `/test_stend/`.

## Железные правила стенда

1. **Отдельная папка, ничего не размазываем.** Весь стенд — в новом маленьком
   Django-app (рабочее имя `fest`, каталог `fest/`): `urls.py`, тонкие вьюхи-рендеры
   (`views.py` — только `render(...)` шаблона, **без логики**), `templates/fest/*.html`,
   `static/fest/*` (свои css/js/картинки). Никаких `models.py`/`migrations` не заводим,
   пока не понадобятся (для демо — не понадобятся).
2. **Один префикс URL — `/test_stend/`.** Подключается **одной строкой** в
   `myproject/urls.py`: `path('test_stend/', include('fest.urls'))`. Прод-URL'ы не
   трогаем; ни один существующий адрес не меняет поведение.
3. **Вьюхи — чистые рендеры статики.** Каждая страница демо — вьюха вида
   `def fest_page(request): return render(request, 'fest/fest_page.html')`. Данные на
   странице — «рыба» прямо в шаблоне (нарисованные цифры/списки). Кнопки — ссылки на
   соседние демо-страницы или JS-попап «TBA».
4. **Ядро ВЦ — только читаем визуально, не мутируем.** Переиспользуем `nexus.css`,
   вёрстку, компоненты. Никакие сервисы/модели ВЦ демо не вызывает и не меняет.
   Аккаунты гостя в демо — **не аккаунты ВЦ** (см. README §0): просто «как будто
   вошёл», без реальной аутентификации.
5. **Общие файлы правим минимально и подписываем.** Единственная ожидаемая правка —
   подключение `fest.urls` и (возможно) регистрация app в `INSTALLED_APPS`. Каждая
   правка помечается `# fest_platform: <зачем>` и заносится в
   [core-touchpoints.md](core-touchpoints.md).
6. **Свою навигацию в общий сайдбар ВЦ не пихаем.** Прод-пользователи не должны видеть
   стенд. Навигация между демо-страницами — внутри самих демо-страниц (свой хедер/меню).
7. **Feature-toggle не обязателен** (стенд и так изолирован под `/test_stend/` и не
   меняет прод), но раздел легко «спрятать», просто не публикуя ссылку.
8. **Статика** — в `fest/static/fest/`; после добавления обязателен
   `collectstatic --noinput` (в проекте `ManifestStaticFilesStorage`, иначе прод падает
   с «Missing staticfiles manifest entry»). Это единственный реальный подводный камень.
9. **Тесты** для статичного демо — по минимуму: достаточно smoke-теста «страница
   отдаётся 200». Прод-тесты (`blog.tests`) должны продолжать проходить без изменений —
   это и есть критерий «ничего не сломали».

## Что берём из ядра (визуально) vs. что своё

| Берём из ВЦ (read-only, визуал) | Своё в `fest/` |
|---|---|
| `nexus.css`, темы, вёрстка, компоненты | Шаблоны `templates/fest/*` (витрина, маркет, ЛК, кабинет) |
| Роутинг Django (отдать шаблон) | Свои `static/fest/*` (css/js/картинки феста) |
| Визуал достижений (для бейджей гостя) | JS-заглушки (countdown, попап «TBA») |

## Почему так безопасно для прода

- Нет новых моделей → **нет миграций** → схема БД прода не меняется.
- Нет вызовов сервисов ВЦ → поведение ядра не затрагивается.
- Всё под `/test_stend/` → ни один боевой URL не пересекается.
- Единственные правки общих файлов — подключить app и URL, обе подписаны и
  зафиксированы в реестре.

## Если дойдёт до контракта

Демо **выбрасывается или переносится** в отдельный проект (см. README §0). Здесь мы
намеренно **не** строим «фундамент под будущее» — только красивую картинку. Поэтому и
не заводим модели/сервисы: они всё равно будут переписаны в отдельном продукте.
