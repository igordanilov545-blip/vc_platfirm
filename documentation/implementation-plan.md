# План реализации платформы Волонтёрского центра

> Пошаговый план **под текущую кодовую базу**. Опирается на `architecture.md`, `access-control.md`, `db.md`, `reports.md`.
>
> **Порядок реализации (по решению заказчика):**
> 1. Основной функционал: **обработка заявок + ведение статистики**.
> 2. **Профили волонтёров** (отдельные публичный / расширенный / внутренний уровни).
> 3. **Интеграция ТГ-бота** в систему.
>
> **Ключевые технические решения:**
> - Backend — **Django + DRF** (единый REST API для будущих Mini App / Web Platform / бота). Уже написанный `data_base/data_controller.py` переиспользуется как service-слой под сериализаторами/вьюсетами, а не выбрасывается.
> - **PostgreSQL** с самого начала (не SQLite).
> - Схема БД приводится к обновлённому `db.md` **сразу, на Этапе 1**, до бизнес-логики.
> - Django Admin как «панель менеджера» **не используется** — весь функционал через DRF API (и позже общий фронтенд).

## Этап 0. Приведение окружения в порядок

> ✅ ВЫПОЛНЕНО (реализовано как server-rendered Django-приложение с шаблонами и сессионной аутентификацией — без DRF, по решению заказчика; см. примечание в начале файла). БД — SQLite на время разработки через `django-environ` (`.env`), с возможностью переключения на Postgres одной переменной `DB_ENGINE`; сам Postgres не поднят локально (недоступен пароль администратора).

Цель: рабочее, воспроизводимое окружение до изменения моделей.

1. **PostgreSQL**: убрать дублирующий SQLite-блок `DATABASES` в `settings.py`, оставить Postgres. Поднять локальную БД (Docker или локальный сервис). Прекратить трекать `db.sqlite3` (в `.gitignore`).
2. **Конфиг через окружение**: `SECRET_KEY`, `DEBUG`, `ALLOWED_HOSTS`, параметры БД — из переменных окружения/`.env` (например, `django-environ`). Секреты — не в репозиторий.
3. **Зависимости**: добавить в `requirements.txt` — `djangorestframework`, `psycopg2-binary`, `django-environ`, `openpyxl`/`pandas` (импорт Excel), `djangorestframework-simplejwt` (задел под веб-аутентификацию, Этап 3 профилей/бота). `INSTALLED_APPS += ['rest_framework']`.
4. **Часовой пояс**: `TIME_ZONE` → `Europe/Moscow` (даты меро, «за последний месяц» в churn, сезоны). `USE_TZ=True` оставить.
5. Проверка: `python manage.py check`, `migrate` на чистой Postgres проходит.

## Этап 4. Заявки — создание, импорт, обработка (ПРИОРИТЕТ 1, часть A)

> ✅ ВЫПОЛНЕНО. Форма создания заявки, импорт из Excel с превью (`blog/services/import_applications.py`) — включая расширение сверх исходного плана: если мероприятие из файла не найдено, строка не отбрасывается, а помечается для авто-создания мероприятия (даты по умолчанию сегодня, поддержка периода дат → `EventDay` на каждый день); кэш мероприятий/пользователей в рамках одного импорта, чтобы не плодить дубли. Матчинг заявки с профилем (`blog/services/applications.py::find_matching_user`) — по telegram_username → phone → ФИО (без проверки на опечатки — это осталось нереализованным). Обработка (approve/reject) с правами менеджера/ТЛ своего меро, авто-создание participations на все дни при approve, пересчёт `recruit_status`. Тестов дедуп-поведения/матчинга/прав нет.

1. **Модель выдачи заявок**: `ApplicationSerializer` + `ApplicationViewSet`. Список с фильтрами (по `event`, `status`, требованиям), точное число заявок, **дубли не скрываются** (актуальная — последняя).
2. **Создание заявки** (`POST /applications`): из формы; `submitted_at`=время подачи, `created_at`=время загрузки (для бота совпадут).
3. **Импорт из Excel** (рефакторинг `prossed.py` + `read_data.py` в модуль `services/import_applications.py`):
   - Парсинг `.xlsx` (openpyxl/pandas), маппинг колонок в поля `Application`.
   - **Два времени**: `submitted_at` из формы (колонка времени подачи), `created_at` — момент загрузки.
   - Валидация построчно → превью (создать / обновить / ошибки) → подтверждение → коммит. (Синхронно на первой версии; вынос в очередь — позже, см. Этап 8-бот/будущее.)
   - Эндпоинты `POST /applications/import` (превью) и подтверждение импорта.
4. **Матчинг заявки с профилем** (`services/match_user.py`, бизнес-правило 5 `db.md`): поиск существующего user по `telegram_username` → `phone` → ФИО; если не найден — создать профиль по данным заявки с проверкой на опечатки (нормализация телефона/username, предупреждение о «почти совпадении», чтобы не плодить дубли).
5. **Обработка заявки** (`PATCH /applications/{id}`): approve/reject.
   - Права: менеджер — на всех; тим-лидер — только на своих меро (Этап 2).
   - `rejected` = «резерв» (отдельного статуса нет); при недоборе ранее отклонённые можно принять.
   - Проставить `assigned_at`, `assigned_by`.
6. **approved → participations**: при одобрении автоматически создать `Participation` на **все** `event_days` меро (бизнес-правило 4); ТЛ затем удаляет лишние дни.
7. **Пересчёт `recruit_status`**: `closed`, когда одобренных заявок ≥ `const.recruit_close_ratio` × Σ`volunteer_needed` (бизнес-правило 10). Явка на это не влияет.
8. Тесты: дедуп-поведение, матчинг, контекстные права ТЛ, авто-создание participations, закрытие набора.

## Этап 5. Участие и статистика (ПРИОРИТЕТ 1, часть B)

> ✅ В основном ВЫПОЛНЕНО. `blog/services/stats.py`: простановка явки с пересчётом кэш-агрегатов (`recalc_user_aggregates`), churn (`apply_churn_no_show`, `apply_churn_activity_decay`, блэклист по порогу), `recruit_status_for_event`, `close_season` (carryover). Отчёт за период — полная аналитика из `reports.md` (`blog/services/reports.py` + `report_period.html`): воронка, эффективность набора, нагрузка персонала, retention/churn, проблемные зоны, сравнение периодов. **Не реализовано**: графики (время отклика, время публикации, funnel-диаграмма, динамика по неделям — сейчас только табличные данные), экспорт в Excel/CSV, периодическая задача/команда для `close_season` (функция есть, но не вызывается по расписанию/вручную из UI), сезоны не управляются менеджером через интерфейс (только через `Season` в БД напрямую). Тестов пересчёта агрегатов/churn/carryover нет.

1. **Простановка явки** (`PATCH /participations`): `attended` / `absent_excused` / `absent_unexcused`, часы. Права: ТЛ на своих меро, менеджер везде. Менеджер может редактировать часы вручную.
2. **Пересчёт кэш-агрегатов** пользователя при изменении `participations.status` (сигнал Django или сервис-функция): `total_hours`, `season_hours`, `total_event_count`, `season_event_count` — только по `attended`; обновление `last_event_at`.
3. **Churn** (бизнес-правило 9):
   - при `absent_unexcused` → `churn_score += const.churn_no_show_penalty`;
   - списание за активность `churn_score -= const.churn_activity_base / e^(N+1)`, где N — меро за последний месяц;
   - при `churn_score ≥ const.churn_blacklist_threshold` → `status='blacklisted'` до следующего сезона;
   - проставление churn — **ручное действие ТЛ** по волонтёру своего меро (отдельный эндпоинт), плюс авто-начисление при `absent_unexcused`.
4. **Аналитика/отчёты** (read-only DRF, по `reports.md`), в порядке приоритета для обработки заявок и статистики:
   - воронка набора (подано → одобрено → явка → unexcused), эффективность набора (% закрытия слотов), нагрузка персонала;
   - отчёт за период (неделя/месяц/сезон), retention/churn, проблемные зоны;
   - стратегия: лёгкие — on-the-fly; тяжёлые (отчёт за период) — кэш-агрегаты. Экспорт в Excel/CSV — отдельный эндпоинт на тех же агрегатах.
5. **Сезоны** (бизнес-правило 11): управление датами (менеджер); при закрытии сезона — снимок ненулевого churn в `churn_history`, затем обнуление/половинное списание по `const.churn_carryover_min_seasons`; обнуление `season_*`; авто-создание бессрочного сезона, если следующий не задан, + флаг «нужно задать дату конца» для плашки. Реализуется как management-команда/периодическая задача.
6. Тесты: пересчёт агрегатов, формула churn (начисление + списание + порог), carryover при закрытии сезона.

Тестов на схлопывание уровней/корректность контекста ТЛ нет.

> После того как заявки/статистика работают, собираем именно **профили** с тремя уровнями видимости.

1. **Трёхуровневая выдача** одним эндпоинтом `GET /users/{id}` через выбор сериализатора по роли запрашивающего и правилу «владелец/менеджер/ТЛ-контекст»:
   - 👁 **публичный**: ник, часы/меро (всего и за сезон), список прошедших меро, статус «Звёздочка ⭐» (`total_hours ≥ const.pgas_hours_threshold`);
   - 👤 **расширенный** (владелец + менеджер + ТЛ по правилу 5): ФИО, контакты, возраст/пол, история заявок, пул благодарственных писем, любимые категории;
   - 🔒 **внутренний** (менеджер + ТЛ по правилу 5): статус, churn (текущий + `churn_history`), исключения из требований, конверсия заявок, динамика активности, комментарии.
2. **Контекстный доступ тим-лидера** (правила 5–6 `access-control.md`): ТЛ видит расширенный+внутренний профиль чужого волонтёра, только пока идёт набор/меро его мероприятия и этот волонтёр подал заявку/участвует. Реализовать проверку в permission/сериализаторе.
3. **Комментарии к волонтёру** (`user_comments`): менеджер видит все; ТЛ — только по правилу 5; волонтёр — **никогда**. Эндпоинты создания/чтения.
4. **Благодарственные письма — генерация на лету**: `GET /users/{id}/letters/{event_id}` → взять `event.letter` (`thank_you_letter_templates`), подставить ФИО, отдать PDF. **PDF не хранится.** (Рендер — reportlab/weasyprint или подстановка в шаблон; файл-шаблон — из media storage, см. ниже.)
5. **Профили тим-лидера и менеджера** (по `reports.md`): доп. публичные поля ТЛ (кол-во меро как ТЛ, дата назначения); внутренний профиль менеджера (контакты, KPI). У ТЛ отдельного внутреннего профиля нет.
6. Тесты: три уровня не схлопываются в один флаг; ТЛ-контекст открывается/закрывается корректно; волонтёр не видит комментарии.

## Этап 7. Медиа и генерация писем (по мере надобности профилей)

1. **Media storage** (S3-совместимое, провайдер — открытый техдолг из `architecture.md` разд.5): presigned URL для загрузки, в БД только ключ/ссылка (`media_key`/`media_url`, nullable).
2. Приватность: файлы-**шаблоны** писем — приватные (менеджеры); фото меро — публичные.
3. Загрузка фото — единый `POST /media/upload`.
4. Генерация PDF письма on-the-fly (Этап 6.4) читает файл-шаблон из хранилища.
> Можно отложить, если на первых порах шаблоны писем лежат локально; тогда медиа-хранилище подключается перед продом.

## Этап 8. Интеграция ТГ-бота (ПРИОРИТЕТ 3)

1. **Фреймворк и режим**: выбор (aiogram/python-telegram-bot); webhook для прода (long polling для локальной отладки). Отдельный сервис/процесс, общается с backend через тот же DRF API.
2. **Идентификация**: по `telegram_id` из апдейта; создание записи `users` при первом `/start`, если её нет.
3. **Первое касание — веб-креды**: бот предлагает задать `login`/`password` для Web Platform → `POST /auth/set-web-credentials` (бизнес-правило 8, `architecture.md` 2.1). Тот же эндпоинт — для сброса пароля (2.2).
4. **Команды бота**: моя статистика (часы/меро), список открытых мероприятий (ближайшие 7), подписка на новые меро.
5. **Диспетчер уведомлений** (очередь исходящих в бота): новая заявка → ТЛ/менеджеру; смена статуса заявки → волонтёру; новое меро → рассылка; готовое письмо → ссылка на скачивание. Ретраи при сбоях Telegram API.
6. **initData-аутентификация**: валидация подписи Telegram WebApp на бэкенде — задел под будущий Mini App (единый способ для Telegram-канала).
7. **JWT для Web** (`architecture.md` 2.3): access+refresh, logout, инвалидация при смене пароля/блокировке — эндпоинты `POST /auth/login|refresh|logout`. (Нужно вместе с веб-входом; можно реализовать здесь же, т.к. пароль устанавливается через бота.)

## Этап 9. Асинхронные задачи (по мере роста нагрузки)

> До этого момента тяжёлые операции допустимо делать синхронно. Выносим в очередь (Celery/Redis), когда объёмы вырастут.

1. Импорт Excel (парсинг/валидация/коммит) — из синхронного в фоновый с прогрессом.
2. Пересчёт агрегатов и churn — сигнал/задача, если синхронный пересчёт станет тяжёлым.
3. Плановые задачи сезона (закрытие/carryover/обнуление `season_*`) — по расписанию.
4. Диспетчер уведомлений в бота — с ретраями.
5. Генерация PDF писем — в задачу, если рендер тяжёлый.

## Этап 10. Тестирование, безопасность, запуск

1. **Тесты**: юнит (дедуп заявок, матчинг, пересчёт статистики, churn, контекстные права ТЛ, видимость комментариев) + интеграционные критичные сценарии из `architecture.md` (заявка→обработка→уведомление; импорт Excel; закрытие смены→пересчёт).
2. **Безопасность** (`access-control.md` разд.4): аудит, что все 🔒/👤 разделы закрыты на уровне API, а не UI; логирование действий менеджеров (кто/когда сменил статус заявки, поставил комментарий/churn/статус волонтёра); ПДн (телефон/email/ДР) — политика хранения и хостинг; бэкапы БД и медиа.
3. **Запуск**: staging-пилот с 1–2 менеджерами и группой волонтёров → итерация по фидбеку → прод, мониторинг ошибок (Sentry-подобный), краткая инструкция для менеджеров/ТЛ.

## Этап 11. После запуска (бэклог, вне MVP)

1. Калибровка формулы churn по данным первого сезона.
2. Self-service портал для организаторов (`architecture.md` разд.6, п.8).
3. Полноценная система достижений/бейджей (сейчас «Звёздочка» — производный признак).
4. Web Platform / Mini App как единый фронтенд поверх готового API (отдельная фронтенд-работа; API к этому моменту уже покрывает все роли).
5. Расширение аналитики (сегментация, прогноз явки).
