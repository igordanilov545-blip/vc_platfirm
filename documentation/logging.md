# Логирование платформы Волонтёрского центра

> Как устроены логи в проекте, куда они пишутся, какие правила соблюдать при
> добавлении новых записей. Конфигурация — в [`myproject/settings.py`](../myproject/settings.py)
> (`LOGGING`), точка получения логгеров — [`blog/logging_utils.py`](../blog/logging_utils.py).

---

## 1. Три независимых канала

Требование: **логи бота, логи прямого взаимодействия с БД и логи веб-приложения
хранятся отдельно**. Поэтому в проекте три канала, каждый в свой файл в каталоге `logs/`:

| Канал | Логгер (префикс) | Файл | Что сюда пишем |
|---|---|---|---|
| **WEB** | `vc.web.*` | `logs/web.log` | Всё веб-приложение: вьюхи (`blog/views.py`), веб-сервисы (`blog/services/*`), аутентификация Web / Mini App / Login Widget, публикация и завершение мероприятий, обработка заявок из веба, Excel-импорт. Сюда же падают ошибки самого Django (`django`, `django.request`). |
| **BOT** | `vc.bot.*` | `logs/bot.log` | Telegram-бот: сборка бота (`tg_bot/bot.py`), сервис-слой бота (`tg_bot/services.py`), диспетчер уведомлений (`tg_bot/notifier.py`), команда `run_bot`. Сюда же логи библиотеки `aiogram`. |
| **DB** | `vc.db.*` | `logs/db.log` | Прямой слой доступа к данным — **только** `data_base/data_controller.py`: изменяющие операции (INSERT/UPDATE), в т.ч. `create_record_generic`. |

Каналы разведены **по именам логгеров**, а конфиг `LOGGING` направляет каждый
префикс в свой `RotatingFileHandler`. `propagate: False` не даёт записям
«протекать» между каналами и в корневой логгер.

### Почему именно так

- Бот и веб — **разные процессы** (веб под WSGI/Passenger, бот — отдельный
  `manage.py run_bot`). Разнеся их логи по файлам, мы не смешиваем два потока
  событий и можем `tail -f` нужный.
- Прямой слой БД (`data_controller`) — единственная точка, где происходят
  фактические INSERT/UPDATE «мимо» бизнес-сервисов. Отдельный `db.log` даёт
  аудиторский след изменений данных, не зашумлённый веб-трафиком.

## 2. Как получать логгер в коде

Никогда не создавайте логгер «руками» через `logging.getLogger(__name__)` —
имя не попадёт в нужный канал. Используйте хелперы из `blog/logging_utils.py`:

```python
from blog.logging_utils import get_web_logger   # или get_bot_logger / get_db_logger

logger = get_web_logger(__name__)               # -> 'vc.web.blog.views'
logger.info('Заявка подана через веб: application=%s', application.id)
```

- `get_web_logger(__name__)` — для кода веба (`blog/views.py`, `blog/services/*`,
  `blog/auth_backends.py`, `blog/middleware.py`).
- `get_bot_logger(__name__)` — для всего под `tg_bot/` и команды `run_bot`.
- `get_db_logger(__name__)` — **только** внутри `data_base/data_controller.py`.

> Пограничный случай: `tg_bot/services.py` вызывает функции `data_controller`.
> Запись «бот сделал X» идёт в `bot.log` (логируем в сервисе бота), а сам факт
> «в БД появилась строка» — в `db.log` (логирует `data_controller`). Это не
> дублирование, а две точки зрения на одно событие: бизнес-намерение и мутация данных.

## 3. Что логировать (и что нет)

Инструментируем **ключевые точки**, а не каждую функцию. Логируем:

- **Аутентификацию и смену прав:** вход (веб-пароль, Login Widget, Mini App,
  ссылка из бота), установку/сброс веб-кредов, выдачу/снятие ролей, попадание
  в блэклист.
- **Смену состояния бизнес-сущностей:** подача заявки, обработка (approve/reject,
  по заявке и по смене), отмена заявки волонтёром, публикация/рассылка/завершение
  мероприятия, простановка явки, закрытие сезона.
- **Пакетные операции:** результат Excel-импорта (created/updated/skipped),
  массовое одобрение заявок.
- **Внешние сбои:** ошибки отправки в Telegram (outbox, запросы оценки), исчерпание
  ретраев — на уровне `WARNING`/`ERROR`.
- **Мутации прямого слоя БД:** INSERT/UPDATE в `data_controller` (канал DB).

**Не логируем:** чтения (`get_*`-функции `data_controller`), рендер страниц без
сайд-эффектов, значения паролей/токенов/`initData`, полный текст личных сообщений.

### Уровни

| Уровень | Когда |
|---|---|
| `DEBUG` | Детали для отладки (напр. «не удалось снять клавиатуру — сообщение уже изменено»). В прод-файлы не попадает при `LOG_LEVEL=INFO`. |
| `INFO` | Нормальные значимые события (вход, подача/обработка заявки, публикация меро, доставка уведомления). Основной рабочий уровень. |
| `WARNING` | Отклонённая попытка входа, неудачная отправка в Telegram, блэклист, невалидный `initData`/токен. Ожидаемые, но требующие внимания. |
| `ERROR` / `exception` | Непойманные ошибки. В цикле диспетчера уведомлений — `logger.exception(...)` в `except`, чтобы поймать трейсбек, не роняя цикл. |

### Формат сообщений

- Пишем **по-русски**, кратко, в настоящем/прошедшем времени факта:
  `'Заявка обработана целиком: application=%s status=%s by=%s subject=%s'`.
- Идентификаторы — через `%s`-подстановку (ленивую), **не** через f-строку:
  `logger.info('user=%s', user.id)`, а не `logger.info(f'user={user.id}')`.
  Так форматирование не выполняется, если уровень отключён.
- Указываем ключевые id (`event=`, `application=`, `participation=`) — по ним потом
  ищут в логах. ФИО/телефон/текст сообщений в лог **не** пишем.

### Кто совершил действие: `actor()`, `by=` и `subject=`

Каждое действие по возможности логируем с указанием, **кто** его совершил, а где
уместно — и **над кем/чем**. Для единообразия используем хелпер
`blog.logging_utils.actor(user)`:

```python
from blog.logging_utils import get_web_logger, actor
logger = get_web_logger(__name__)

logger.info('Заявка обработана: application=%s by=%s subject=%s',
            app.id, actor(request.user), actor(app.user))
# -> ... by=user=42(ivan_petrov) subject=user=17(petya)
```

`actor()` возвращает `user=<id>(<логин|tg-username|system_username>)` — id плюс
читаемый хендл (без ПДн). Особые случаи: `user=anonymous` (неаутентифицированный),
`user=system` (фон/задача без инициатора), `user=?` (объект не передан/неизвестен).

Соглашение о полях:

| Поле | Смысл |
|---|---|
| `by=` | **актор** — кто выполнил действие (тим-лидер/менеджер/волонтёр/аноним). |
| `subject=` / `applicant=` | **над кем** действие: чью явку проставили, чью заявку обработали, кому выдали роль. |
| без `by=` | действие пользователь совершает над собой (подача/отмена своей заявки, регистрация) — актор и есть субъект. |

В канале **DB** (`data_controller`) актор проброшен через параметры там, где вызывающий
его знает: `update_application_status(..., assigned_by=...)`,
`update_participation_status(..., actor_user=...)`. Где актор недоступен на этом слое
(напр. `create_record_generic`), в логе остаётся только субъект/сущность — это
осознанное ограничение (слой не всегда знает инициатора).

## 4. Конфигурация и ротация

Всё настраивается через `.env` (значения по умолчанию — в скобках), см. `.env.example`:

| Переменная | Назначение |
|---|---|
| `LOG_DIR` (`<проект>/logs`) | Каталог для файлов логов. Создаётся автоматически при старте. |
| `LOG_LEVEL` (`INFO`) | Порог для наших каналов и консоли. |
| `LOG_MAX_BYTES` (`5242880` = 5 МБ) | Размер файла до ротации. |
| `LOG_BACKUP_COUNT` (`5`) | Сколько ротационных копий хранить (`web.log.1` … `web.log.5`). |

- Обработчики — `logging.handlers.RotatingFileHandler` (кодировка UTF-8), поэтому
  файлы не растут бесконечно.
- При `DEBUG=True` все три канала **дополнительно** дублируются в консоль — удобно
  при локальной разработке. В проде (`DEBUG=False`) вывод только в файлы.
- Логи **не коммитятся** — `logs/`, `*.log`, `*.log.*` в `.gitignore`.

## 5. Эксплуатация

```bash
# следить за конкретным каналом в реальном времени
tail -f logs/bot.log
tail -f logs/web.log

# найти всё по конкретной заявке через все каналы
grep "application=42" logs/*.log

# отследить путь пользователя (веб-вход → подача → обработка)
grep "user=17" logs/web.log logs/bot.log
```

На проде (Beget/Passenger) веб-канал пишется процессом WSGI, бот-канал — процессом
`run_bot`. Оба используют один и тот же `LOG_DIR`, файлы разные — конфликтов записи нет.

## 6. Чек-лист при добавлении логов

1. Определи канал: это веб, бот или прямой слой БД? Возьми соответствующий
   `get_*_logger(__name__)`.
2. Логируй **событие/намерение**, а не каждую строку кода. Одна значимая запись
   на бизнес-действие.
3. Уровень: `INFO` для нормы, `WARNING` для отклонений/сбоев, `exception` в `except`.
4. Ленивое `%s`-форматирование, только id и коды, без ПДн и секретов.
5. Указывай актора через `actor(user)` (`by=…`), а где есть — и субъекта (`subject=…`).
   Если слой не знает инициатора — пробрось его параметром от вызывающего.
5. Не добавляй логи в `get_*`-читалки `data_controller` — только в изменяющие операции.

## 7. Ротация под Windows (2026-11-11)

`runall` запускает сайт и бота отдельными процессами, оба пишут в одни `logs/*.log`.
Стандартный `RotatingFileHandler` на Windows не может переименовать файл, открытый
другим процессом: при достижении `LOG_MAX_BYTES` он падал с `PermissionError` на
каждой записи, и строки терялись. Теперь в `LOGGING` — `blog.log_handlers.SafeRotatingFileHandler`:
неудачная ротация не теряет запись (дописывается в текущий файл), повтор — не чаще
раза в минуту. Файл может временно превысить предел — это ожидаемо.
