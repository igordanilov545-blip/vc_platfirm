> **Охват «всё время / за период».** Отчёты по человеку, по волонтёрам и по организации
> генерируются **двумя отдельными прогонами**: либо целиком «за всё время», либо целиком

> метрики без временной привязки (контакты, дата регистрации) печатаются одинаково.

### 📈 График «Жизнь мероприятия» (таймлайн)

> Главный визуальный блок отчёта по меро. Одна горизонтальная **временная шкала** от
> создания меро до простановки часов; на ней — ключевые события меро вертикальными
> засечками, а подачи заявок — точками снизу. Позволяет одним взглядом увидеть весь
> жизненный цикл: когда опубликовали, когда пошли заявки, как рассылка их подстегнула,
> когда прошли дни и когда всё закрыли.

**Ось X** — время (от `events.created_at` до последнего из: закрытие / простановка часов).

**Вертикальные засечки (события меро):**

| Засечка | Источник | Стиль |
|---------|----------|-------|
| ▎ Создание | `events.created_at` | серая тонкая |
| ▎ Публикация (анонс) | `events.published_at` | синяя — открывает подачу заявок |
| ▎ Пост в канале | `events.post_published_at` | голубая пунктирная |
| ▎ Рассылка | `events.broadcast_sent_at` | оранжевая; **если рассылок было несколько — несколько линий** (см. примечание) |
| ▎ День(и) меро | каждый `event_shifts.day` | зелёная полоса (интервал `start_time…end_time`), несколько — по числу смен + подпись сколько волонтеров было вида "было n/k" |
| ▎ Закрытие на платформе | момент `events.event_status='finished'` (по логу/`updated`) | тёмно-зелёная |
| ▎ Часы на Добро.ру | `participations.dobro_ru_logged_at` (первый/последний) или флаг `events.dobro_ru_hours_logged` | фиолетовая |

> **Несколько рассылок.** В текущей модели хранится только `broadcast_sent_at` — момент
> **первой** рассылки (повторные рассылки для добора момент не перезаписывают, см.
> `views.event_broadcast`). Чтобы честно рисовать **несколько** линий рассылки, нужно
> отдельное хранилище моментов рассылок (напр. лог рассылок / таблица `event_broadcasts`).
> До этого на таймлайне гарантированно есть одна линия рассылки; остальные — техдолг,
> помечено в макете как «(повторные рассылки — после доработки модели)».

**Точки заявок (снизу, над осью):**

- Каждая подача заявки (`applications.submitted_at`, при пустом — `created_at`) — точка.
- **Форма/цвет = финальный статус заявки:** ● одобрена (зелёная) · ○ резерв/отклонена
  (серая) · ◐ новая (жёлтая) · ✕ отменена волонтёром (красная, `cancelled`).
- **Кластеризация при наложении.** Если точки по времени близки (перекрываются при текущем
  масштабе — окно, напр., 1–2% ширины оси), они **объединяются в один кружок с числом
  внутри** — «N заявок», диаметр растёт с N. По клику/в приложении — разворачивается в список.
  В DOCX рядом с кластером печатается подпись `×N`.
- Опционально второй ряд точек — **обработка заявок** (`assigned_at`): видно лаг между
  «подал» и «обработали».

```
Заявки:            ● ●●   ⑤    ●  ○      ●●●②      ○
                   │ ││   │    │  │       │││       │
─────┬─────┬───┬───┴─┴────┴────┴──┴───▓▓▓─┴─────┬───┴──►  время
   создан публ. пост  рассылка          дни    закрытие  часы Добро.ру
                                       меро
   └── набор идёт ──────────────────┘
```

**Что читается с графика (зачем он):**
- пустота между «публикацией» и первой заявкой → анонс не зашёл / канал слабый;
- всплеск точек сразу после «рассылки» → рассылка сработала (обоснование повторных рассылок);
- большинство заявок в последний день перед меро → набор «в последний вагон», риск недобора;
- большой лаг «подал → обработали» → узкое место в работе ТЛ/менеджера с заявками.

> Этот же таймлайн **переиспользуется** в комплексном отчёте за период — по одному на
> каждое меро периода (см. раздел «Комплексный отчёт»).

# Отчёт простановки часов на Добро.ру EXCEL (DONE)

> Добро.ру. Простановка происходит **вне системы**; в системе менеджер отмечает факт. (у меро есть поле статус выставлены ли ему часы на добро ру, нужно фильтровать по нему) 
> Формат — **Excel** (удобно выделять/фильтровать/копировать), при необходимости и DOCX.

### Что и зачем

Менеджеру нужно удобно увидеть: **на какую ссылку**, **кому** и **сколько часов** проставить.
Ключевой принцип — **два разреза** одного набора данных. Менеджер выделяет блок и аккуратно
проставляет всё разом.

В отчёт попадают attended-участия (`hours > 0`) на меро с `dobro_ru_link_kind ∈ {shared, unique}`.
Меро с `none` исключаются..


### описание: 
Стрнаница 1:
Делаем таблицу колонка с ФИО, где с каждой новой, колонка "сколько часов в сумме", колонка "мероприятий в сумме" по данному волонтеру (там должны идти именно формулы счет суммы и количества соответственно), а дальше колонки, хедерами в которых являются  ссылка добро ру по этому/этим  + Названия меро. их на пересечении у нас или пустота (если человек не участвовал в мероприятии) или количество часов, которое необходимо ему выставить за данное мероприятие (сумма по всем сменам) 
Если нам попадается общая ссылка по множеству мероприятий, то мы исходим из того, что у нас ссылка оринетированная архитектура на данной странице и мы через запятую перечисляем все меро привязанные к данной ссылке. в пересечении данной ссылки и человека, итоговая ссумма по часам, за мероприятия по данной ссылке

# Отчёт по волонтёрам (DOCX)

> «Идём по каждому волонтёру подряд и пишем всю инфу». Структура: **сводная статистика
> сверху** (по всей выборке), затем **подряд в алфавитном порядке** (по фамилии, имени)
> карточки каждого волонтёра. Карточка волонтёра = блоки A–D «Отчёта по человеку» (E/F не
> включаются — это отчёт именно про волонтёрскую активность).
>
> **Охват (два отдельных прогона):** «за всё время» либо «за период».
> **Выборка:** все волонтёры у которых есть хотя бы одна заявка за это время (даже если заявка была отклонена)

```
┌───────────────────────────────────────────────────────────┐
│  ОТЧЁТ ПО ВОЛОНТЁРАМ                                       │
│  Охват: {всё время | период …}   Выборка: {все|активные|…} │
│  Волонтёров в отчёте: {N}                                  │
├───────────────────────────────────────────────────────────┤
│  СВОДКА ПО ВЫБОРКЕ (сверху, до карточек)                    │
│    Всего волонтёров ......... {N}                          │
│    Суммарно часов ........... {SUM total_hours по выборке} │
│    Суммарно участий ......... {SUM участий}                │
│    Ср. часов на волонтёра ... {часы / N}                   │
│    Новых за охват ........... {COUNT created_at в охвате}  + их список│
│    Со «Звёздочкой» ПГАС ..... {COUNT season_hours ≥ порог} + их список│
│    В блэклисте .............. {COUNT status=blacklisted} + их список  │
```

# Отчёт за период (общий) DOCX

> Компактный **аналитический** отчёт за период — то, что описано в [reports.md](reports.md) §7:
> сводка достижений, воронка набора, эффективность набора, нагрузка персонала, retention/churn,
> проблемные зоны, сравнение с прошлым периодом + графики. Это **самостоятельный** документ
> (не путать с «Комплексным» — тот включает этот отчёт как первую часть и добавляет
> мероприятия и людей подряд).
>
> Выпускается в **двух вариациях** (строгое подмножество): 🌐 **внешний** (обезличенный, для
> руководства/грантодателей) и 🔒 **внутренний** (для менеджеров, с именами и внутренней кухней).
> Макет блоков 1–8 — это раздел «Комплексный отчёт за период» ниже (блоки 1–8), но **без**
> части «мероприятия подряд» и «люди подряд». То есть:
>
> **Отчёт за период (общий)** = блоки 1–8 (сводка · воронка · эффективность набора · нагрузка
> персонала · retention/churn · проблемные зоны · сравнение · графики).
> **Комплексный отчёт** = общий отчёт + мероприятия периода подряд + таблица работы с заявками
> + отчёт по каждому волонтёру периода.

Все блоки, метрики и графики общего отчёта уже расписаны:
- поля/источники и доступ 🌐/🔒 — [reports.md](reports.md) §7;
- макет блоков 1–8 — раздел «Комплексный отчёт за период» ниже (первые 8 блоков).

Отдельно печатать здесь ASCII не будем, чтобы не дублировать — общий отчёт = первые 8 блоков

# Комплексный отчёт за период (DOCX-пакет, для менеджеров)

> **Толстый пакет** за один охват-период. Состоит из четырёх частей подряд:
> 1. **Сводная аналитика** (блоки 1–8 ниже) — это и есть «Отчёт за период (общий)».

|--------|----------------|-------|
| **Жизнь мероприятия (таймлайн)** ⭐ | события меро засечками + подачи заявок точками (с кластеризацией «×N») | цельная картина цикла: сработала ли рассылка, когда пошли заявки, лаг обработки |
| Кривая набора | кумулятивно заявки/одобрения во времени от публикации | скорость набора, «в последний вагон» |
| Заявки по сменам | сколько подано/одобрено/пришло на каждую смену | какая смена недобрана |
| Воронка по меро | подано → одобрено → явка → неявка | где теряются люди на этом меро |

⚠️ Для честных **нескольких линий рассылки** нужен лог моментов рассылок (сейчас хранится только первый).

### Отчёт по человеку / по волонтёрам
| График | Что показывает | Зачем |
|--------|----------------|-------|
| Динамика активности | часы/участия по месяцам | ритм волонтёра, спад активности |
| Timeline churn по сезонам | `churn_history` во времени | как менялась надёжность |
| Разбивка участий по категориям | кольцевая/столбчатая | интересы волонтёра |
| (по волонтёрам) Топ-10 по часам | горизонтальные бары | лидеры сообщества |
| (по волонтёрам) Гистограмма часов | распределение волонтёров по часам | «ядро» vs «разовые» |
| (по волонтёрам) Распределение churn | бакеты churn, порог линией | сколько на грани блэклиста |

### Отчёт Добро.ру
| График | Что показывает | Зачем |
|--------|----------------|-------|
| Прогресс простановки | проставлено X из N по каждой ссылке (прогресс-бары) | что ещё не закрыто |
| Часы к простановке по ссылкам | столбчатая: сумма часов на ссылку | объём работы по ссылкам |

> **Общий принцип графиков** (см. также skill `dataviz`): обезличенные агрегаты → 🌐 (внешний
> отчёт); всё, где видно конкретных людей → 🔒 (внутренний). Кластеризация точек при наложении
> (как на таймлайне меро) — обязательна везде, где точек может быть много.
