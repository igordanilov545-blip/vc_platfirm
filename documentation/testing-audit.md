## 1. Что тестируется сейчас

Тесты — `blog/tests/*.py`, обычный `django.test.TestCase` + `Client`, без моков
внешних сервисов (Telegram Bot API не дёргается — уведомления идут через
`bot_outbox`, см. [logging.md](logging.md) §5, поэтому веб-тесты его не трогают).
Фабрики объектов — `blog/tests/factories.py` (без `factory_boy`, простые хелперы с
дефолтами). Раннер — `python manage.py test blog.tests`. Отдельной тестовой БД/фикстур
не требуется — Django поднимает тестовую БД автоматически. **Coverage-инструмента,
Selenium/Playwright и вообще браузерных тестов в проекте нет.** У `tg_bot/` (сам процесс
бота) собственного каталога тестов нет — его сервис-слой покрывается тестами из
`blog/tests/`, но хендлеры/клавиатуры/middleware бота — нет ни одного теста.

Прогон подтверждён вживую в рамках этого аудита: **84/84 теста зелёные** (~1.5 сек),
`python manage.py check` — чисто, `makemigrations --check --dry-run` — миграции
синхронны с моделями (no drift).

**Важный контекст происхождения тестов** — по докстрингам файлов и
`documentation/refactor-plan.md`, эта сетка создавалась не как систематическое
покрытие функционала, а как **safety net под конкретный рефакторинг** (перенос
прямого ORM-доступа `views.py`/`tg_bot/services.py` в `data_controller`, «Фаза 2»/«Фаза
5»). Прямая цитата из refactor-plan.md: «сетка безопасности с нуля до 80 тестов
(контроллер, вьюхи, потоки, модерация, бот, форматтеры, const-driven)». Это объясняет
наблюдаемый в разделе 2 перекос: глубоко тестируются именно те инварианты, которые
могли сломаться при переносе ORM, а не полнота покрытия по всей поверхности приложения.

## 2. Что НЕ тестируется (пробелы)

### 2.1 CI не запускает тесты вообще — критично — ✅ ЗАКРЫТО (см. §5)
`.github/workflows/deploy.yml` по push в `main` сразу идёт на VPS и
`docker compose up -d --build`, никакого `manage.py test` перед деплоем нет. То есть
все 90 существующих тестов гоняются только вручную (или не гоняются). Красный тест не
блокирует прод.

### 2.2 Покрытие маршрутов (`blog/urls.py`) — точечное — 🟡 БОЛЬШАЯ ЧАСТЬ ЗАКРЫТА (см. §5)
В `blog/urls.py` **133 маршрута** (`blog/views/` — порядка 150+ функций, из них
самые крупные модули: `reports.py` ~32, `events.py` ~21, `settings_hub.py` ~19,
`analytics.py` ~17, `applications.py` ~17). `test_views_smoke.py` и остальные файлы
вместе бьют примерно по 25-30 уникальным именам маршрутов — то есть черновая оценка
покрытия по числу эндпоинтов составляет **~20%**, и распределено оно крайне
неравномерно: ядро процесса (заявки → одобрение → участие → модерация) покрыто
хорошо, периферия — почти нет. Целые группы вообще не тронуты ни одним тестом
(ни smoke, ни flow):

- **Отчёты и экспорт** (`reports/period/*`, `report_period_export`, `report_period_pdf`,
  `report_bundle`, `report_dobro_export`, `report_event_pdf/export`, `report_person_pdf`,
  `report_volunteers_pdf/export`, `report_organization_pdf`, `report_complex_pdf`) — ни
  один из PDF/Excel-генераторов не запускается тестом ни разу. Это самый рискованный
  участок: чистая логика в `blog/services/report_*`, `charts.py`, `docx_report.py`,
  `pgas_pdf.py` — сложная, легко ломается при рефакторинге, а регрессия себя проявит
  только у пользователя, скачавшего пустой/битый файл.
- **Excel-импорт заявок** (`import_preview`, `import_commit`,
  `blog/services/import_applications.py`) — ключевой доменный инвариант («дедупликация
  по паре человек+мероприятие», см. CLAUDE.md §4) нигде не тестируется, хотя описан как
  «легко ошибиться, тихие последствия».
- **CRUD справочников** (`locations`, `organizations`, `organizers`, `requirements`,
  `categories`, `perks`, `quick-create/*`) — ни создание, ни редактирование, ни удаление
  не покрыты.
- **Аналитика** (`analytics/*` — 13 маршрутов: ping/leave/click, данные для графиков,
  даунтаймы, логи) — ноль тестов.
- **Публичные страницы без входа** (`public_event_list`, `public_event_detail` по
  токену, `public_experience`) — не покрыты, а это единственный анонимный поверхностный
  слой приложения (риск утечки данных/403 обхода).
- **Профиль и внешний опыт** (`profile_edit`, `complete_profile`,
  `external_experience_*`, письма `letter_view`) — не покрыты.
- **Аутентификация** — ни один из 4 каналов входа
  (`telegram_login_callback`, `tg_link_login`, `webapp_auth`, `login_view`) не имеет
  теста, при том что это самый чувствительный код в проекте (HMAC-проверка подписи
  Telegram, одноразовые токены) — см. coding-principles §3.
- **Организаторы/организации** — детальные страницы и связка орг↔организатор (недавняя
  фича из `f09fff9`) без тестов.

Ветки ошибок (403/404/невалидная форма) проверены у единиц маршрутов, и это только
happy path даже там, где тесты есть.

### 2.3 Сервисный слой веба — большие пробелы
Из 25 файлов `blog/services/*` ни разу не упомянуты в тестах (проверено grep'ом по

быть хотя бы дымовой тест регистрации хендлеров/роутеров при импорте).

### 2.5 Management-команды — не покрыты — ✅ ЗАКРЫТО частично (close_season/recalc_stats/dedupe_applications — см. §5)
17 команд в `blog/management/commands/` (`close_season`, `recalc_stats`,
`dedupe_applications`, `read_data`, `create_manager`, `process_notifications`,
`purge_analytics`, `record_downtime`, `checker`, `set_webhook`, `seed_*`, `runall`) —
ноль тестов. Важно не путать два разных решения: `refactor-plan.md` осознанно
**исключил management-команды из требования «доступ к БД только через
data_controller»** (это операционный слой, логировать одноразовые команды не имеет
смысла) — но это решение **не касалось тестов**, оно относилось к архитектурному
правилу §5 CLAUDE.md. `close_season` и `recalc_stats` напрямую трогают агрегаты и
часовые показатели пользователей по всей базе — тихая поломка здесь означает неверную
статистику у всех волонтёров разом, и это никак не покрыто.

### 2.6 «Приложение запускается» / инфраструктурный smoke — ✅ ЗАКРЫТО (см. §5)
- Нет теста, что `python manage.py check` включён в тестовый прогон/CI (сейчас это
  отдельный ручной шаг по чеклисту agent-workflow §8).
- Нет теста консистентности миграций (`makemigrations --check --dry-run`) — риск
  расхождения моделей и миграций, которое проявится только в проде.
- `healthz` (есть вьюха `views.healthz`) не тестируется, хотя это ровно тот эндпоинт,
  для которого «работоспособность системы» — весь смысл существования.
- Нет теста для `collectstatic` (CLAUDE.md явно предупреждает: без него тесты/прод
  падают с «Missing staticfiles manifest entry» — то есть про это здесь фактически
  «известно, что можно сломать», но автоматической страховки нет).

### 2.7 Фронтенд/JS-поведение
Ожидаемо (Django + ванильный JS, без фреймворка) — нет никакого инструмента для
проверки клиентского поведения: `initCategoryChips`, `initDatepickers`,
`initInfiniteScroll`, `initReportTableTools`, `CompanionTour` и т.д.
(`blog/static/blog/js/*`) не тестируются вообще, ни юнитами (нет JS-тест-раннера), ни
браузерными e2e. Это осознанный пробел (для монолита на Django Templates это нормально
закрывать вручную через `/verify`), но стоит явно зафиксировать как границу
покрытия — «страницы рендерятся и содержат нужную разметку» можно проверить
Django-тестами (`assertContains` на `data-*` атрибуты), а «клик действительно

### 2.8 Ролевая матрица прав — тестируется частично, роль тим-лидера — вообще нет — ✅ ЗАКРЫТО (см. §5)
`roles.py` (`is_manager`, `is_team_leader`, `is_team_leader_of_event`,

## 3. Предложения: что и как добавить

Порядок — по риску (что сломается тихо и больно) и легкости внедрения.

### Приоритет 1 — инфраструктурная страховка (дёшево, ловит «всё упало»)
1. **Включить тесты в CI.** Добавить джоб `test` в `.github/workflows/` (или отдельный
   workflow `ci.yml` на `pull_request`/`push`), который поднимает Postgres-сервис (или
   гоняет на SQLite, раз `DB_ENGINE` переключаемый) и запускает
   `python manage.py check && python manage.py makemigrations --check --dry-run &&
   python manage.py test blog.tests`. Деплой из `deploy.yml` можно оставить как есть,
   но в идеале сделать зависимым от зелёного CI (`needs:`/`workflow_run`).
2. **Smoke-тест "приложение поднимается"**: `manage.py check` уже вызывается вручную —
   обернуть в `TestCase`, который просто импортирует все `urls.py`
   (`django.urls.get_resolver().url_patterns`) и проверяет, что resolve не падает —
   ловит опечатки в путях/циклические импорты сразу.
3. **Тест `healthz`**: `GET /healthz/` → 200 + ожидаемое тело — 5 минут работы, а
   именно этот эндпоинт используют внешние мониторинги.
4. **Тест консистентности миграций** — отдельный `TestCase`/CI-шаг, который гоняет
   `makemigrations --check`, чтобы не полагаться на память агента.

### Приоритет 2 — покрытие всех страниц (по образцу test_views_smoke.py)
5. **Расширить `test_views_smoke.py` до полного прохода по `urls.py`.** Практический
   приём: собрать таблицу `(url_name, required_role, expected_status)` и
   параметризовать тест (`for name, role, code in ROUTES: ...`), а не плодить метод на
   каждый маршрут вручную — так и новый урл в `urls.py` попадёт под тест, если
   поддерживать список рядом. Отдельные группы:
   - все справочники (`locations/organizations/organizers/requirements/categories/perks`)
     — list/create/edit/delete по разу, с проверкой, что запись реально появляется/
     пропадает в БД (не только код 200);
   - все `reports/*` — минимум «страница/экспорт не падает 500» на пустых и
     непустых данных (регрессия PDF/Excel обычно всплывает как `TemplateSyntaxError`
     или исключение в `openpyxl`/`reportlab`, что легко ловится smoke-тестом);
   - `analytics/*` — хотя бы happy path на каждый data-эндпоинт (JSON, код 200,
     ожидаемые ключи).
6. **Auth-каналы отдельным файлом `test_auth_flows.py`**: HMAC-подпись `webapp_auth`
   (валидная/невалидная/просроченная), `tg_link_login` (валидный токен/просроченный/
   уже использованный), `login_view` (логин/пароль, блэклист блокирует вход — согласно
   coding-principles §3 «блэклист закрывает вход по всем каналам» — эту фразу стоит
   прямо застраховать тестом).
7. **Excel-импорт `test_import_applications.py`**: дедуп по (человек, мероприятие),
   повторная загрузка обновляет, а не плодит; матчинг
   `telegram_username → phone → ФИО`; отменённые заявки не воскрешаются; импортной
   заявке всегда есть привязанный `User` (в т.ч. `import:*` telegram_id) — это прямые
   цитаты инвариантов из CLAUDE.md §4, которые сейчас не имеют ни одного теста.

### Приоритет 3 — ACL и ролевая матрица
8. **`test_roles_matrix.py`**: таблица «роль × действие × ожидаемый результат» для
   ключевых операций (обработка заявки, просмотр чужого профиля, редактирование меро) —
   отдельно для волонтёра, ТЛ на своём меро, ТЛ на чужом меро, ТЛ на завершённом своём
   меро (по инварианту должен потерять права), менеджера. Фабрика `make_team_leader`
   в `factories.py` уже существует и не используется ни одним тестом — с неё и начать.

## 4. Как считать «полное покрытие» практически

Дословное «каждая кнопка работает» через unit-тесты Django недостижимо буквально (клик
— это JS в браузере). Реалистичная декомпозиция:

- **Django TestCase** гарантирует: маршрут резолвится, вьюха не падает 500, ACL
  отдаёт верный код, HTML/JSON-ответ содержит ожидаемые данные и `data-*`-атрибуты,
  на которые навешивается JS (т.е. «кнопка на странице есть и правильно размечена»).
- **`/verify` вручную** (уже в чеклисте agent-workflow §8) закрывает «клик по кнопке
  в браузере действительно делает то, что нужно» для конкретной фичи в моменте
  разработки.
- **Playwright** (если решим внедрить, п.11) — единственный способ автоматизировать
  именно «клик работает» на постоянной основе, но это отдельная, дорогая инвестиция;
  внедрять точечно на самые критичные сквозные сценарии, не пытаться покрыть всё.

Практическая метрика прогресса — не «% строк», а: (а) % маршрутов из `urls.py` с
хотя бы одним smoke-тестом, (б) все инварианты из CLAUDE.md §4 и coding-principles §6
имеют явный тест с комментарием-цитатой правила (стиль уже задан в
`test_const_driven.py`/`test_moderation_flows.py` — держаться его же).

### Как проверить актуальность утверждения «100% маршрутов покрыто»
Утверждение верно **на момент второго прохода** и означает «есть хотя бы один
HTTP-запрос к маршруту в каком-то тесте», не «все ветки/статусы/роли покрыты». Чтобы
перепроверить после будущих изменений:
```
grep -oE "name='[^']+'" blog/urls.py | sed "s/name='//;s/'//" | sort > /tmp/all.txt
grep -rhoE "reverse\(['\"][a-z_0-9]+['\"]" blog/tests/*.py | sed -E "s/reverse\(['\"]//;s/['\"]//" | sort -u > /tmp/tested.txt
comm -23 /tmp/all.txt /tmp/tested.txt   # маршруты без единого reverse() в тестах
```
Оговорка: маршруты, вызываемые через `reverse(name)` с `name` — переменной цикла (не
строковым литералом), grep не поймает — их нужно проверять вручную (в этом проекте
это `_assert_list_route` в `test_references_crud.py`, покрывающий 5 list-вьюх
справочников через параметризованный хелпер).
