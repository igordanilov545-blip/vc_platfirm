# Каталог пользовательских сценариев

> Единый сводный список **всех** сценариев, которые обрабатывает платформа —
> по ролям и точкам первого касания. Составлен из фактического кода (хендлеры бота
> `tg_bot/handlers/*`, вьюхи `blog/views.py`, сервисы `blog/services/*`,
> `tg_bot/services.py`). Служит основой интерактивных CJM-деревьев в [`cjm/`](cjm/).
>
> Каждый переход в CJM-деревьях снабжён оценочной эмоцией пользователя:
>
> - 😖 **fak-эмоция** — неудобно / долго / непонятно / упёрся в стену;
> - 🙂 **ok-эмоция** — ожидаемо, всё работает как надо;
> - 🤩 **wow-эмоция** — система сделала сверх ожиданий.

## Точки первого касания (корни деревьев)

Пользователь впервые попадает в систему одним из трёх способов — это три корня
дерева волонтёра:

1. **Через бота** (`/start`) — самый частый путь. Создаётся гость.
2. **Через подачу заявки на сайте** — вход через Telegram (Login Widget / ссылка /
   Mini App), затем заявка. Веб-регистрации «с нуля» нет — аккаунт всё равно
   рождается через Telegram.
3. **Через появление заявки из Excel-файла** — менеджер импортирует выгрузку;
   профиль волонтёра создаётся системой автоматически (служебный `import:*` id),
   и человек «встречается» с системой уже постфактум — когда позже приходит в бота
   и обнаруживает, что его данные уже знают (🤩).

## A. Сценарии волонтёра

### A0. Первое касание и регистрация
- **A0.1** `/start` в боте → создаётся гость, приветствие, меню гостя.
- **A0.2** Возврат зарегистрированного (`/start`) → приветствие по имени, ролевое меню.
- **A0.3** Регистрация: имя → телефон (можно «Пропустить» или поделиться контактом) → готово.
- **A0.4** Deep-link `?start=weblogin` → сразу ссылка входа на сайт (без регистрации).
- **A0.5** Автоподтягивание профиля из прошлых заявок при первом касании
  (`sync_user_from_applications`) — телефон/ФИО уже известны системе (🤩).

### A1. Мероприятия и заявки (бот)
- **A1.1** `/events` — список открытых мероприятий с кнопкой «Подать заявку».
- **A1.2** Подача заявки на меро. Гость → сначала мягко ведут в регистрацию, затем
  предлагают вернуться к подаче (сохранённый `pending_event_id`).
- **A1.3** Повторная заявка на то же меро → не молчание, а предложение
  посмотреть/изменить/отменить существующую (правило 7d).
- **A1.4** `/myapps` — активные заявки (new/approved) на актуальные меро.
- **A1.5** Изменение заявки → создаётся новая запись с обновлёнными функцией/ролью.
- **A1.6** Отмена заявки → проверка срока (`late_cancel_hours`) → обязательная причина.
- **A1.7** Набор закрыт / меро снято / блэклист → понятные отказы.

### A2. Мероприятия и заявки (веб / Mini App)
- **A2.1** Публичный список открытых меро без входа (гость видит дашборд-витрину).
- **A2.2** Публичная карточка меро по share-ссылке (`/events/s/<token>/`), без входа.
- **A2.3** Подача заявки с сайта. Незаполненный профиль → плашка «заполните ФИО/ТГ/телефон»
  со ссылкой на профиль, с возвратом (`next`) к подаче.
- **A2.4** Выбор конкретных смен чипами (`selected_shifts`) — участие только по выбранным.
- **A2.5** Редактирование своей заявки (вместо дубля).
- **A2.6** Отмена своей заявки (то же правило срока/причины, что в боте).

### A3. Статистика, подписки, обратная связь
- **A3.1** `/stats` — часы/меро за всё время и за сезон, признак «Звёздочка ПГАС» ⭐.
- **A3.2** `/subscribe` — тумблер уведомлений о новых меро.
- **A3.3** Оповещение о новом меро (рассылка) — приходит подписанным, кроме уже подавших.
- **A3.4** Запрос оценки после участия (через 3 ч) → оценка 1–10 + опц. комментарий.
- **A3.5** «Мой опыт»: внешний волонтёрский опыт (не в статистике) + публичная
  read-only ссылка «скопировать опыт» (`/profile/exp/<token>/`).

### A4. Профиль и доступ к сайту
- **A4.1** Редактирование профиля (ФИО, ТГ, телефон, почта, ВК, дата рождения, о себе).
- **A4.2** `/webaccess` — установка логина/пароля для входа на сайт без Telegram.
- **A4.3** Вход на сайт: логин/пароль, Login Widget, одноразовая ссылка из бота, Mini App.
- **A4.4** Сброс веб-пароля из бота (тот же `/webaccess`) → инвалидация веб-сессий.

## B. Сценарии тим-лидера (контекстные — только свои меро)

- **B1** `/myevents` — мои меро как ТЛ, с числом новых заявок.
- **B2** Просмотр заявок на рассмотрении по меро.
- **B3** Обработка заявки: одобрить / в резерв (approve → participation + пересчёт статистики).
- **B3a** Обработка отдельной смены заявки (per-shift decision), не затрагивая другие смены.
- **B4** «Одобрить все» заявки по меро одним действием.
- **B5** Явка: Был / Отсутствовал уважительно / Неявка без предупреждения. Пересчёт
  часов и churn; неявка без предупреждения → штраф churn, при пороге → блэклист.
- **B6** Простановка/правка часов и признака «полная смена» (ручной override).
- **B7** Расширенный профиль волонтёра — только пока меро не завершено и волонтёр в нём.
- **B8** Внутренний комментарий к волонтёру (виден менеджерам и автору в рамках меро).
- **B9** Ручное открытие/закрытие набора на смену.
- **B10** Тумблер `notify_applications` (получать ли карточки новых заявок).
- **B11** Лента изменений заявок меро (ApplicationChangeLog) — отметить прочитанной.

## C. Сценарии менеджера (полный доступ)

### C1. Мероприятия
- **C1.1** Создание меро (черновик) + быстрые «quick-add» справочников (локация,
  организация, организатор, категория) прямо из формы.
- **C1.2** Смены: добавить/изменить/удалить (даты, время, потребность, локация).
- **C1.3** Назначение персонала (менеджеры/тим-лидеры) на меро.
- **C1.4** Публикация меро → открывается подача заявок.
- **C1.5** Рассылка-оповещение подписанным (отдельно от публикации, можно повторно).
- **C1.6** Завершение меро: чеклист условий + обязательное `people_helped`.
- **C1.7** Отметка «часы на Добро.ру выставлены» (после завершения).

### C2. Заявки и участники
- **C2.1** Обработка любой заявки на любом меро (approve/reject, по заявке и по смене).
- **C2.2** «Все заявки» / «Необработанные заявки» — сводные списки, массовая обработка.
- **C2.3** Excel-импорт заявок: превью (создать меро / создать/обновить/пропустить) →
  подтверждение. Дедуп по (человек, меро), лог изменений, авто-создание профилей.

### C3. Справочники и люди
- **C3.1** CRUD: локации, организации, организаторы (+ история взаимодействий), категории.
- **C3.2** Список пользователей, карточки профилей, внутренние комментарии.
- **C3.3** Выдача/снятие ролей (тим-лидер / менеджер). Менеджеру авто-выдаётся ТЛ.
- **C3.4** Настройки: правка бизнес-констант (`Const`) с капчей.

### C4. Отчёты
- **C4.1** Отчёт за период (по меро/волонтёрам), поиск меро, экспорт XLSX/PDF.
- **C4.2** Отчёт по конкретному меро (XLSX/PDF), сводный «bundle».
- **C4.3** Страница/экспорт «Добро.ру».
- **C4.4** Благодарственное письмо волонтёру (генерация на лету, `/profile/<u>/letters/<e>/`).

## D. Жизненный цикл мероприятия (сквозной, дерево «Мероприятие»)

Отдельное дерево — не роль, а сущность, проходящая стадии; в каждой стадии
действуют разные роли (🔗 связь ролей):

1. **Извне** — запрос от организатора/партнёра (вне системы).
2. **Черновик** — менеджер заводит меро, смены, персонал.
3. **Опубликовано** — открыт набор, идут заявки (веб/бот/Excel).
4. **Идёт набор** — ТЛ/менеджер обрабатывают заявки; автоматика закрывает набор при пороге.
5. **Проходит** — день(и) меро; фиксируется явка.
6. **Прошло** — даты кончились, меро ещё не закрыто менеджером.
7. **Завершено** — менеджер прошёл чеклист, указал `people_helped`.
8. **Пост-обработка** — часы на Добро.ру, запросы оценок, благодарственные письма, отчёты.
